# Phase 26 — UI Design Contract

> Visual and interaction contract for Phase 26 M1 Canary + Cutover Gates. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.

---

## Phase UI Boundary

Phase 26 is an operations and cutover gate phase, not a marketing redesign. The UI work must make ticketing readiness, QR visibility, payment safety, rollback state, and first-24-hour monitoring legible to a one-person operator while preserving the existing Grabit admin shell and public booking language.

Allowed touched surfaces:

| Surface | Contract |
|---------|----------|
| Gate Ledger readiness surface | Show every cutover gate as an auditable row with exact state, evidence, owner approval, rollback/close trigger, and no-go reason |
| Direct deploy watch | Present the 100% direct deploy, 15-minute strict watch, revision IDs, critical smoke checks, and rollback readiness without traffic-split canary language |
| Dedicated test-event rehearsal | Make test-event isolation, dry-run cleanup counts, backup/restore-point status, and real-event denylist visible before destructive cleanup |
| QR completion surfaces | Payment complete page and My Page/ticket detail must show or directly expose an active QR ticket state after confirmed payment |
| Toss test/live cutover | Keep test-key rehearsal, redacted live-key smoke, and `BOOKING_ENABLED=true` enablement as separate visual steps |
| Monitoring and first-24h watch | Show queue, lock, payment, QR, refund, Cloud Run, Sentry, Cloudflare, and sellout signals with the first-2h and 24h cadence |

Blocked surfaces:

| Surface | Reason |
|---------|--------|
| Cloud Run traffic-split canary controls | D-05 supersedes older roadmap wording; Phase 26 uses direct deploy plus strict watch |
| Full field-staff mobile QR scanner and ticket use-processing UI | Phase 27 scope |
| Event-day entry monitor, offline scan sync, settlement export, retrospective UI | Phase 27 scope |
| New public fanmeet landing page, new brand palette, or hero redesign | Existing event detail surface remains the launch surface |
| Secret viewer or raw provider payload display | Toss keys, payment keys, QR tokens, cookies, OTPs, PII, and raw CSV values must never be exposed in UI or artifacts |
| Real Girl Rules cleanup or load-target controls | Rehearsal must use a dedicated test performance/showtime only |

Source: `.planning/phases/26-m1-canary-cutover-gates/26-CONTEXT.md`, `.planning/phases/26-m1-canary-cutover-gates/26-RESEARCH.md`, `.planning/REQUIREMENTS.md`, `.planning/ROADMAP.md`, `apps/web/components.json`, `apps/web/app/globals.css`, current `apps/web/app/admin/*`, `apps/web/components/admin/*`, and prior Phase 24/25 UI contracts.

## Layout Contract

### Admin Operations Layout

| Area | Contract |
|------|----------|
| Page title row | Title on the left, gate validation or evidence-refresh CTA on the right, with secondary filters below |
| Readiness summary | 4-6 compact stat cards: `PASS`, `BLOCKED/FAIL`, `ACCEPTED_RISK`, `CONFIG_READY_NOT_DRILLED`, missing evidence, next no-go blocker |
| Main ledger | Dense table first; row click opens a right detail pane on desktop or full-height sheet/dialog on mobile |
| Detail pane | Evidence list, failure reason, approver, approval timestamp, compensating monitoring, rollback/close trigger |
| Sticky action area | Final cutover actions stay disabled until the ledger validator permits them; disabled state must explain the blocking row |

### Desktop/Mobile Density

| Breakpoint | Contract |
|------------|----------|
| `xl` and above | Use table plus right detail pane for Gate Ledger and monitoring rows |
| `md` to `lg` | Stack filter/search controls above tables; keep evidence detail in `Dialog` or below the selected row |
| Mobile | Sidebar collapses to `Sheet`; gate rows become stacked cards with the state badge, gate ID, requirement, and next action visible without horizontal scroll |

### Information Order

1. Go/no-go state.
2. Gate or metric name.
3. Requirement ID.
4. Evidence freshness and target environment.
5. Failure or caveat reason.
6. Approval state, approver, and rollback/close trigger.

The first screen of any Phase 26 admin surface must show whether live ticketing can proceed. Operators must not need to open every row to discover a blocker.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline icon gaps, compact badge padding, evidence metadata gaps |
| sm | 8px | Filter-control gaps, gate row metadata, dialog footer button gaps |
| md | 16px | Default card padding, form spacing, ledger section spacing |
| lg | 24px | Page-section separation, watch checklist spacing, detail-pane spacing |
| xl | 32px | Major dashboard gaps and monitoring section breaks |
| 2xl | 48px | Empty states and QR completion spacing |
| 3xl | 64px | Page-level top/bottom spacing only |

Exceptions:

- New or touched mobile controls must be at least `44px` high or wide.
- Primary gate validation, evidence refresh, and QR follow-up buttons stay at least `44px` high; final cutover and rollback buttons stay `48px` high.
- Dense admin table cells may use `8px` vertical padding only if the clickable row target remains at least `44px`.
- Gate status badges may use compact `4px/8px` padding but must not be the only click target.
- QR images or QR cards must keep a stable square area of at least `180px` on mobile and `220px` on desktop if an actual QR image is rendered.
- Sticky footers must preserve `16px` vertical padding and must not cover warning, validation, or rollback copy.

Source: `apps/web/app/globals.css`, existing admin density, and Phase 24/25 UI contracts.

## Typography

Use exactly these four roles for new or touched Phase 26 UI. Do not introduce a new display scale.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Readability rules:

- Use `Display` only for top-level admin page titles and public completion title text.
- Use `Heading` for card titles, selected gate detail title, QR ready title, and modal titles.
- Use `Label` for gate states, requirement IDs, metric labels, evidence timestamps, table headers, and buttons.
- Use `Body` for failure reasons, compensating monitoring, rollback instructions, and user-facing QR guidance.
- New authored text uses only weights `400` and `600`.
- Gate state, payment safety, QR status, rollback, cleanup, and accepted-risk copy must never drop below `14px`.
- IDs, revision names, order prefixes, and redacted provider identifiers may use UI monospace but only at `14px` or `16px`.

Source: inherited core scale from Phase 23/24/25 and confirmed by `apps/web/app/globals.css`.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Cards, dialogs, ledger tables, detail panes, admin sidebar/header, QR ticket cards |
| Secondary (30%) | `#F5F5F7` | Workspace background, table headers, muted evidence bands, disabled/pending metadata |
| Accent (10%) | `#6C3CE0` | Primary CTA, focus ring, active tab/filter, selected gate row, QR follow-up CTA |
| Destructive | `#C62828` | `FAIL`, `BLOCKED`, rollback, close-booking, destructive cleanup, payment/seat safety failures |

Accent reserved for: primary gate validation CTA, active sidebar item, selected tab/filter, selected ledger row, focus ring, active watch step, and QR follow-up CTA. Accent must not be used for `PASS`, `FAIL`, `BLOCKED`, accepted-risk warnings, or destructive cutover controls.

Phase-specific state colors:

| State | Surface | Text | Usage |
|-------|---------|------|-------|
| `PASS` / healthy / QR active | `#F0FDF4` | `#15803D` | Gate passed, smoke healthy, QR issued, refund job healthy |
| `FAIL` / `BLOCKED` / rollback trigger | `#FEF2F2` | `#C62828` | Cutover blocker, user-path critical failure, unsafe payment/seat state |
| `ACCEPTED_RISK` | `#FFFBEB` | `#8B6306` | Owner-approved non-PASS gate with explicit rollback trigger |
| `CONFIG_READY_NOT_DRILLED` | `#FFFBEB` | `#8B6306` | Config evidence exists but drill is not PASS evidence |
| Missing / unreviewed / no-go | `#F5F5F7` | `#6B6B7B` | Empty evidence, pending operator review, disabled cutover action |
| Informational / selected row | `#F3EFFF` | `#6C3CE0` | Selected evidence row, neutral watch instructions, QR pending guidance |

Color rules:

- Status must never rely on color alone. Every state chip must include the exact state text or a clear Korean label.
- `ACCEPTED_RISK` and `CONFIG_READY_NOT_DRILLED` remain amber and visibly non-PASS even when the ledger validator allows owner-approved progress.
- Destructive red is reserved for real stop/rollback/close-booking or financial/seat safety risks.
- Do not show green security-complete or payment-live-complete states unless the corresponding Gate Ledger row is `PASS`.
- Provider-native Toss UI keeps provider styling inside the widget; do not recolor provider controls with Grabit accent.

Source: `apps/web/app/globals.css`, Phase 26 D-01 through D-30, and existing admin state chips.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `게이트 검증하기` |
| Empty state heading | `등록된 게이트 증거가 없습니다` |
| Empty state body | `Gate Ledger 행을 생성하고 각 게이트의 상태와 증거 파일을 연결하세요. 빈 행이 있으면 BOOKING_ENABLED=true는 no-go입니다.` |
| Error state | `게이트 상태를 불러오지 못했습니다. 새로고침 후 다시 시도하고, 반복되면 Gate Ledger artifact와 API 상태를 확인하세요.` |
| Destructive confirmation | `BOOKING_ENABLED=true 활성화`: `모든 필수 게이트가 PASS 또는 승인된 ACCEPTED_RISK인지 확인했습니다. 실패 시 즉시 닫을 기준과 rollback trigger를 다시 확인한 뒤 진행하세요.` |

Critical copy set:

| Surface | Copy Contract |
|---------|---------------|
| Gate no-go summary | `아직 라이브 예매를 열 수 없습니다` |
| Gate ready summary | `모든 필수 게이트가 검토되었습니다` |
| Missing gate evidence | `증거가 비어 있어 no-go입니다` |
| Accepted-risk approval | `PASS가 아닌 상태로 진행하려면 실패 게이트, 보완 모니터링, rollback trigger를 기록해야 합니다` |
| Config not drilled | `설정 증거는 있지만 실제 drill PASS는 아닙니다` |
| Direct deploy watch | `100% 직접 배포 후 15분 동안 핵심 경로를 감시합니다` |
| Traffic-split correction | `이 phase는 Cloud Run traffic-split canary를 사용하지 않습니다` |
| Dedicated test event | `전용 테스트 이벤트만 사용합니다` |
| Real event protection | `실제 Girl Rules 이벤트와 실제 사용자/결제/좌석 데이터는 변경하지 않습니다` |
| Cleanup dry-run required | `정리 실행 전 dry-run 결과와 backup/restore-point를 확인하세요` |
| Toss test-key rehearsal | `테스트 키 리허설은 결제 흐름을 검증하지만 라이브 승인 증거가 아닙니다` |
| Toss live-key smoke | `라이브 키는 BOOKING_ENABLED=false 상태에서 먼저 검증합니다` |
| QR ready | `결제가 완료되었습니다. QR 티켓을 바로 확인할 수 있습니다.` |
| QR pending | `결제는 완료되었지만 QR 티켓을 확인하는 중입니다. 잠시 후 새로고침하거나 마이페이지에서 다시 확인하세요.` |
| First-2h watch | `예매 오픈 후 첫 2시간은 5-10분 간격으로 확인합니다` |
| 24h watch | `이후 24시간까지 30-60분 간격으로 상태를 확인합니다` |
| Close-booking trigger | `금융 또는 좌석 안전 기준을 위반하면 즉시 예매를 닫습니다` |

Copy rules:

- Use plain operational Korean inside admin surfaces. Do not use marketing, celebratory, or reassurance-only copy for cutover state.
- State copy must explain the next action: add evidence, approve accepted risk, run smoke, rollback, close booking, or check provider dashboard.
- Never describe `ACCEPTED_RISK` or `CONFIG_READY_NOT_DRILLED` as passed.
- Never write or display raw Toss keys, payment keys, QR tokens, OTPs, cookies, PII rows, or full CSV payloads.
- User-facing QR copy must remain calm and direct. It must not mention scanner, duplicate-scan, offline validation, or field operations in Phase 26.

## Surface Interaction Contract

### Gate Ledger Readiness

| Interaction | Contract |
|-------------|----------|
| State enum | Use exactly `PASS`, `FAIL`, `ACCEPTED_RISK`, `CONFIG_READY_NOT_DRILLED`, `BLOCKED`; no synonyms in persisted gate rows |
| Required columns | Gate ID, requirement, state, environment, evidence freshness, failure/caveat reason, approval state, rollback/close trigger |
| Row detail | Show evidence links, redaction note, actor, timestamp, target env, command/source summary, and latest decision |
| Empty rows | Treat as no-go and render neutral disabled state with `증거가 비어 있어 no-go입니다` |
| Accepted risk | Requires owner/operator name, approval timestamp, failed gate, compensating monitoring, and rollback/close trigger before it can unblock |
| Config not drilled | Must remain amber and non-PASS; if allowed by owner, show the same explicit approval fields as accepted risk |
| Final enable action | `BOOKING_ENABLED=true` CTA stays disabled until all required rows are `PASS` or explicitly approved non-PASS states |

Gate Ledger rules:

- Keep the ledger source of truth in the artifact/API model, not client-only state.
- Row sorting defaults to blockers first: `BLOCKED`, `FAIL`, missing evidence, unapproved `ACCEPTED_RISK`, unapproved `CONFIG_READY_NOT_DRILLED`, then `PASS`.
- Gate filters must include state, requirement, environment, evidence age, and owner-approved/non-approved.
- Disabled cutover actions need an inline reason that names the first blocking gate.
- Toasts are allowed only after a completed refresh or approval save; no blocking decision should be toast-only.

### Direct Deploy Watch

| Interaction | Contract |
|-------------|----------|
| Deploy model | Show `CI/CD green -> 100% direct deploy -> 15-minute watch`; do not render 5%/50% traffic-split steps |
| Watch timer | 15-minute watch uses a clear timer/checklist with health, auth/session, public detail, booking-disabled, queue entry, payment-safe path, and logs |
| Revision context | Show deployed revision ID and known rollback revision ID in redacted/short form |
| Critical failure | Health 5xx, login/refresh failure, public detail 5xx, queue entry 5xx, booking-disabled side effect, or payment unsafe behavior turns the row destructive |
| Rollback action | Rollback button or command reveal uses destructive styling and requires `AlertDialog` confirmation with target revision summary |

Direct-deploy rules:

- The UI must explicitly state that older canary wording is superseded for this phase.
- A green deploy row is not enough; the watch checklist must also pass or be recorded in the Gate Ledger.
- Log snippets in evidence preview must be redacted and clipped. Link to artifacts instead of dumping long logs into the UI.

### Dedicated Test-Event Rehearsal And Cleanup

| Interaction | Contract |
|-------------|----------|
| Test target | Always show dedicated `performanceId`, `showtimeId`, test order prefix, and test marker in a scoped summary |
| Real-data guard | Show a visible warning that real Girl Rules event, real users, reservations, payments, tickets, and seat state are not cleanup targets |
| Dry-run first | Cleanup execution stays disabled until dry-run counts/lists and backup/restore-point evidence are present |
| Unexpected rows | If dry-run returns unexpected rows, show `BLOCKED` destructive state and require manual review |
| Cleanup execute | Requires confirmation that repeats the test IDs/order prefix and denylist protection |

Rehearsal rules:

- Payment-safe/test-key rehearsal copy must say it is not live merchant readiness.
- High-volume k6 states must distinguish queue/read load from sampled booking mutation and tiny payment-safe smoke.
- Never present a generic "reset production data" action.

### QR Visibility And Field-Scan Contract Smoke

| Interaction | Contract |
|-------------|----------|
| Payment complete page | After confirmed payment, show a visible QR-ready state and a primary `QR 티켓 보기` follow-up; if QR is still finalizing, show pending guidance |
| My Page ticket detail | Show active QR ticket state, reservation/payment linkage summary, status, issue time, and event/showtime context |
| QR rendering | If a scannable QR image is rendered, keep it stable, high contrast, square, and not clipped at `320px` width |
| Redaction | Do not display raw QR token/JWT/HMAC or raw `paymentKey`; use masked JTI or status metadata for evidence |
| Field-scan contract | Show only readiness metadata for Phase 27 scanner inputs; do not add manager scan/use-processing controls |

QR rules:

- D-25/D-26 make missing QR visibility a cutover blocker. A payment `DONE` state without visible/access path to active QR must remain `BLOCKED`.
- Complete page and My Page evidence must be consistent: user should not see success on one surface and no QR/ticket on the other.
- QR pending is non-destructive only when payment/reservation state is safe and a retry path exists.

### Toss Test/Live Cutover

| Interaction | Contract |
|-------------|----------|
| Two-step flow | Step 1: live keys injected while `BOOKING_ENABLED=false`; Step 2: enable booking only after Gate Ledger approval |
| Key display | Show only key type/prefix validation (`test_*` or `live_*`) and environment; never show raw key values |
| Server authority | Confirm/query/cancel and webhook re-query evidence belongs under backend/server rows, not frontend widget-only success |
| Payment-safe smoke | Live-key smoke must clearly indicate whether confirm/cancel/query was safely allowed or blocked by provider/operator limits |
| Enable booking | `BOOKING_ENABLED=true` is a high-risk operation with final confirmation and rollback/close trigger summary |

Payment rules:

- Test-key success must not unlock the live gate by itself.
- If Toss review or live keys are unavailable, the gate state is `BLOCKED` or explicitly approved `ACCEPTED_RISK`; never label it `PASS`.
- Widget/client-key initialization and server secret handling are separate checks.

### Monitoring, WAF, And First-24h Watch

| Interaction | Contract |
|-------------|----------|
| Metric cards | Show queue length/admission rate, lock/prepare/confirm success, payment success/failure, QR issuance, refund job failures, remaining seats, and sellout state |
| WAF evidence | Show Cloudflare active rule state, normal pass smoke, and low-volume suspicious challenge/block/rate-limit evidence |
| Alert evidence | Show Sentry alert dry-run, Cloud Run log query state, and business-metric query freshness |
| First-2h cadence | A checklist row repeats every 5-10 minutes for queue/payment/seat/QR/Cloud Run/Sentry/Cloudflare |
| 24h cadence | After the first 2 hours, show periodic 30-60 minute checks until the 24-hour watch completes |
| Close-booking triggers | Duplicate sale, payment-confirm success without reservation/QR, payment failure spike, seat mismatch, queue stuck, or refund/cancel job buildup use destructive state |

Monitoring rules:

- Metrics need timestamps and source labels; stale metrics must be visibly stale, not silently green.
- WAF challenge/block success and normal buyer pass are separate rows.
- A metric card can be green only when the matching Gate Ledger or watch row has current evidence.
- Every critical red state needs a next action: rollback, close booking, check provider, run log query, or contact support path.

## Accessibility And Readability

| Area | Contract |
|------|----------|
| Keyboard | Gate rows, filters, evidence links, QR follow-up, rollback confirm, and accepted-risk approval must be keyboard reachable |
| Focus | Use existing ring token `#6C3CE0`; do not suppress focus outlines on cutover or QR controls |
| Screen reader | Gate validation result, direct deploy watch state, QR pending/ready, and close-booking triggers need `role="alert"` or appropriate live-region behavior |

| Touch target | New or touched mobile controls must be at least `44px`; final cutover/rollback controls should be `48px` |
| Motion | No flashing, shaking, or aggressive urgency animation; respect `prefers-reduced-motion` |
| Data safety | Long IDs wrap or truncate with tooltip/copy affordance; no raw secret or PII is copied into visible text |
| Locale safety | Public QR/booking-disabled copy must remain readable in supported launch locales without horizontal clipping at `320px` width |
