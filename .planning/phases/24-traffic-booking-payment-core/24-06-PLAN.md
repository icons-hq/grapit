| user cancel/refund request -> refund/payment state | Irreversible financial state changes start here. |
| background job -> seat availability | Seat reopen happens outside the original HTTP request here. |
| QR ticket issuance -> user-visible ticket surfaces/email | Signed admission artifacts leave the API here. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-24-18 | T/R | `refund.service.ts` | mitigate | Use explicit refund states, transaction/locking, and idempotent cancel orchestration so duplicate user/provider actions cannot double-refund or hide failure state (Task 1). |
| T-24-19 | T/D | `cancelled-seat-release.worker.ts`, `admin-booking.service.ts` | mitigate | Reopen seats only through delayed jobs or explicit admin manual-open, preventing immediate public availability after every cancel (Task 1). |
| T-24-20 | S/T | `qr-ticket.service.ts` | mitigate | Sign QR tickets with a dedicated `QR_TICKET_SECRET`, persist `qrTokenJti` and `secretVersion`, and expose tickets only after confirmed payment state exists (Task 2). |
</threat_model>
