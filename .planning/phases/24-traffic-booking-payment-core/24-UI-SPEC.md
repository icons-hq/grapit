# Phase 24 — UI Design Contract

> Visual and interaction contract for Phase 24 Traffic + Booking + Payment Core. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.

---

## Phase UI Boundary

Phase 24 extends the existing booking path into a complete test-key flow: queue admission, multi-floor seat selection, payment method expansion, refund preview/state visibility, and immediate QR issuance visibility. It must preserve the existing Grabit visual language, the Phase 23 localization foundation, and the `BOOKING_ENABLED=false` cutover guard until Phase 26 explicitly enables live booking.

Allowed touched surfaces:

| Surface | Contract |
|---------|----------|
| Queue admission page/state | Dedicated full-page waiting state before `/booking`; show position, ETA, remaining seats, and automatic entry behavior |
| Booking seat selection | Existing booking layout plus floor selector, floor-aware summary, dynamic ticket limit copy, and seat-hold visibility |
| Confirm/payment page | Existing single-column confirm flow plus overseas-payment disclaimer consent, payment method expansion, and payment deadline visibility |
| Booking complete / My Page reservation detail | Immediate QR-ready reassurance, refund preview, refund state timeline, and D-1 QR email notice |
| Booking-disabled fallback | Preserve localized amber informational guard when runtime flag blocks booking |

Blocked surfaces:

| Surface | Reason |
|---------|--------|
| Toss live-key cutover, `BOOKING_ENABLED=true`, and launch-open copy | Phase 26 gate |
| Full admin seat operation console and manual reopen UI | Phase 25 scope |
| Field QR scanning, duplicate/tamper scan UI, and offline scan sync | Phase 27 scope |
| New WAF, prewarm, or anti-fraud dashboards | Phase 24 only needs user-facing failure states plus operator runbook artifacts, not new product UI |
| New brand palette, campaign hero, or redesigned public shell | Preserve current Grabit visual language and layout density |

Source: `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`, `.planning/phases/24-traffic-booking-payment-core/24-CONTEXT.md`, `.planning/phases/23-launch-foundation/23-UI-SPEC.md`.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline status/icon spacing, timer label gap |
| sm | 8px | Compact queue metadata rows, seat-row inline gaps, checkbox-label gaps |
| md | 16px | Default section spacing, card padding, form row spacing |
| lg | 24px | Booking section separation, confirm-page block spacing |
| xl | 32px | Major layout gaps, page padding on roomy breakpoints |
| 2xl | 48px | Completion-state separation, large empty-state padding |
| 3xl | 64px | Page-level spacing only; do not use inside booking cards or modals |

Exceptions:

- New or touched interactive controls must be at least `44px` high or wide on mobile.
- Primary booking, payment, refund, and QR-follow-up buttons stay `48px` high.
- Floor selector items may use `40px` height on desktop, but remain `44px` minimum on mobile.
- Icon-only seat removal or back controls may stay visually compact only when the surrounding row remains a `44px`-high hit target.
- The embedded Toss widget may keep provider-native spacing inside the iframe/widget surface.

Source: inherited from `.planning/phases/23-launch-foundation/23-UI-SPEC.md` and confirmed by `apps/web/app/globals.css`.

## Typography

Use exactly these sizes for Phase 24 surfaces. Do not introduce additional font sizes.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Source: inherited from `.planning/phases/23-launch-foundation/23-UI-SPEC.md`, `apps/web/app/globals.css`, and current booking/reservation component patterns.

Readability rules:

- Queue position, countdown time, reservation number, and QR issue metadata may use UI monospace, but only at existing body, heading, or display sizes.
- New Phase 24 text uses only weights `400` and `600`.
- Floor labels, seat labels, and refund state badges must wrap rather than truncate on `320px` width.
- Payment-sensitive and refund-sensitive copy must not shrink below `14px`.
- Countdown emphasis comes from color and weight change, not from larger font jumps.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Booking, confirm, refund, and QR card surfaces; queue page primary surface |
| Secondary (30%) | `#F5F5F7` | Page background, muted summary sections, queue metadata bands |
| Accent (10%) | `#6C3CE0` | Primary CTA, focus ring, active floor selector, active countdown above warning threshold, queue progress highlight |
| Destructive | `#C62828` | Irreversible refund confirmation, blocked behavior, payment deadline at two minutes or less |

Accent reserved for: primary booking/payment CTA, focus ring, active floor selector item, queue admission highlight, active step indicator, and QR-ready follow-up CTA. Accent must not be used for sold/locked seat state, refund failure, or provider branding.

Phase-specific state colors:

| State | Surface | Text / Stroke | Contract |
|-------|---------|---------------|----------|
| Queue waiting / informational | `#F3EFFF` | `#6C3CE0` | Waiting, auto-entry in progress, neutral queue notices |
| Queue warning / low remaining seats / 429 retry | `#FFFBEB` | `#8B6306` | Retry-later state or low-seat caution |
| Blocked / challenge failed / payment deadline critical / refund failed | `#FEF2F2` | `#C62828` | Security block, irreversible risk, deadline-critical, refund failure |
| Success / QR issued / refund completed | `#F0FDF4` | `#15803D` | Payment success, QR ready, refund completed |
| Seat locked or sold | `#D1D1DB` | `opacity: 0.6` | Locked or sold seats are visibly unavailable and not tappable |
| Selected seat | seat tier color | `#1A1A2E` stroke | Keep tier fill color; selection adds dark outline/checkmark instead of recoloring with accent |

Color rules:

- Seat tiers remain the source-of-truth colors from the SVG/tier config. Do not recolor selected seats to purple.
- Overseas payment method logos rendered by Toss keep provider-native branding inside the widget; do not tint them with accent color.
- Status must never rely on color alone. Every status surface needs explicit text.
- Countdown pill stays accent-colored until `02:00` remaining, then switches to destructive red. Do not turn red earlier.

Source: inherited palette from `.planning/phases/23-launch-foundation/23-UI-SPEC.md`, `apps/web/app/globals.css`, `apps/web/components/booking/seat-map-viewer.tsx`, and `apps/web/components/booking/countdown-timer.tsx`.

|---------|------|

| Empty state heading | `선택한 좌석이 없습니다` |

| Error state | `예매 정보를 불러오지 못했습니다. 새로고침 후 다시 시도하고, 계속 실패하면 다시 대기열에 입장하세요.` |
| Destructive confirmation | `예매 취소`: `환불 요청 후에는 되돌릴 수 없습니다. 환불 예정 금액, 환불 수단, 취소 후 좌석 재오픈 지연을 확인한 뒤 진행하세요.` |

| Surface | Copy Contract |
|---------|---------------|

| Security challenge | `보안 확인 후 다시 시도해주세요` |
| Security block | `비정상적인 접근으로 요청이 차단되었습니다. 반복되면 고객센터에 문의해주세요` |
| Dynamic ticket limit helper | `이 공연은 1인 {N}매까지 예매할 수 있습니다` |
| Overseas payment disclaimer checkbox | `해외 결제 및 환불 유의사항에 동의합니다` |
| Overseas disclaimer helper | `KRW 결제, 예상 환율, 수수료, 환불 반영 지연을 확인했습니다` |
| Lock failure recovery | `좌석 점유 시간이 만료되었거나 다른 사용자가 먼저 선택했습니다. 좌석을 다시 선택해주세요.` |
| Refund state labels | `환불 요청됨`, `PG 전달됨`, `환불 처리 중`, `환불 완료`, `환불 실패` |
| Random reopen notice | `취소된 좌석은 즉시 재오픈되지 않을 수 있으며, 잠시 후 다시 판매될 수 있습니다` |
| QR ready reassurance | `결제가 완료되었습니다. QR 티켓은 마이페이지에서 바로 확인할 수 있습니다.` |
| QR email notice | `QR 티켓 안내 메일은 공연 24시간 전에 다시 발송됩니다.` |

Copy rules:

- All new queue, payment, refund, and QR visible copy must ship in `ko`, `en`, `th`, `zh-CN`, and `zh-TW` before Phase 26 canary.
- Payment-sensitive and refund-sensitive copy must use reviewed translations, not raw machine-translation-only text.
- Distinguish queue redirect, 429 retry, security challenge, blocked behavior, payment cancel, payment failure, and lock expiry as separate messages.
- Do not promise immediate seat reopening after user cancellation.
- QR copy must reassure availability immediately after payment without implying scan validation is part of Phase 24.

Source: `.planning/phases/24-traffic-booking-payment-core/24-CONTEXT.md`, `.planning/REQUIREMENTS.md`, current booking/reservation components, and Phase 23 localization contract.

## Surface Interaction Contract

### Queue Admission

| Interaction | Contract |
|-------------|----------|
| Entry point | Queue begins when the user attempts `/booking`, not on performance detail or signup |
| Waiting layout | Full-page state with primary display for queue position, secondary ETA, tertiary remaining-seat count, and non-primary queue/session metadata |
| Admission behavior | Auto-enter booking when admitted; manual `enter now` button is fallback-only if automatic navigation fails |
| Refresh/back handling | Preserve booking state during grace window; after expiry, redirect back to queue with explicit reason copy |
| Blocking requirement | Queue validation is not cosmetic; invalid admission must correspond to API rejection on booking mutations |
| Failure surfaces | Queue redirect, 429 retry, security challenge, and hard block must each have distinct copy and visual states |

Queue UI rules:

- Use one dominant action only after admission. While waiting, do not present a fake active CTA.
- Waiting state must feel transparent, not punitive: show progress context before showing warnings.
- Remaining-seat updates are supportive metadata, not a blinking alert.
- Queue states may use polling, SSE, or Socket.IO under the hood, but the visual contract is stable regardless of transport.

### Multi-Floor Seat Selection

| Interaction | Contract |
|-------------|----------|
| Floor switching | Use a sticky `ToggleGroup` above the seat map; switching floors never clears selected seats or resets the timer |
| Selection summary | Group selected seats by floor label and preserve tier swatch, seat label, and price for every selection |
| Ticket limit | Replace hardcoded `4-seat` copy with event-configured limit in both helper copy and error copy |
| Sold/locked seats | Render as visibly disabled and non-interactive |
| Selected seats | Preserve tier fill color, add dark outline/checkmark, and mirror the selection in summary immediately |
| Post-payment seat changes | Not supported; reservation detail routes users to cancellation/refund instead of seat-swap UI |

Seat-map rules:

- Keep the existing `SeatMapViewer` zoom/pan/minimap behavior. Phase 24 adds floor navigation around it, not a new rendering model.
- On mobile, floor selector and sticky summary must remain reachable without obscuring the map.
- When no seats are selected, the summary uses the empty-state copy above rather than a blank box.
- If a floor has no available seats, show a warning state inside the selector/summary area rather than hiding the floor.

### Timer and Booking Progress

| Interaction | Contract |
|-------------|----------|
| Seat-hold timer | Show a visible seat-hold countdown as soon as the first seat lock exists |
| Payment deadline | Confirm/payment step shows a visible payment countdown with destructive red only at `02:00` remaining or less |
| Timeout behavior | On timeout, release or invalidate the booking state, explain why, and send the user back to a recoverable step |
| Payment failure return | Payment cancel/failure returns the user to a safe booking state with explicit next-step copy |

Timer rules:

- Countdown uses `aria-live="polite"` for routine updates and escalates to assertive announcement at warning threshold.
- Do not animate the timer aggressively. Urgency comes from color shift and copy, not shaking or flashing.
- Timeout recovery must prefer a clear CTA over silent state reset.

### Confirm and Payment

| Interaction | Contract |
|-------------|----------|
| Layout | Keep the current single-column confirm page with stacked `Card` sections and one primary CTA at the bottom |
| Toss widget | Keep the Toss widget as the primary method surface; do not build a parallel custom payment-method gallery |
| Overseas methods | Overseas card, Alipay+, and truemoney require an additional unchecked disclaimer checkbox immediately above the primary CTA |
| CTA enablement | Primary payment CTA stays disabled until widget is ready, required booking terms are checked, and any overseas disclaimer consent is checked |
| Disabled booking guard | When `BOOKING_ENABLED=false`, keep the amber informational guard and prevent payment action creation |

Payment rules:

- Provider-specific disclaimers are outside the generic booking-terms card. They require their own visually separated consent block.
- Display KRW as the primary amount. Any FX estimate is secondary helper text only.
- Payment failure and seat-lock failure need inline recovery blocks, not toast-only feedback.
- Never imply payment is complete until backend confirmation and reservation commit are done.

### Refund and Cancellation

| Interaction | Contract |
|-------------|----------|
| Refund preview | Reservation detail must show refund preview details before the final destructive confirmation |
| Final confirmation | Use `AlertDialog` only for the irreversible confirm step, not for the entire preview/explanation surface |
| State timeline | After request, show user-visible refund progress states: requested, sent to PG, processing, completed, failed |
| Reopen expectation | User-facing copy must state that cancelled seats may reopen later, not immediately |
| Delay handling | If refund stays in a non-terminal state beyond expected timing, show an explicit customer-support CTA |

Refund UX rules:

- The user should see refund amount, refund method, policy deadline, and delay expectation before confirming.
- A failed refund state is operationally important and must remain visible until resolved.
- Do not collapse every non-completed state into a single `취소 처리 중` label.

### QR Issuance and Completion

| Interaction | Contract |
|-------------|----------|
| Immediate reassurance | Booking complete screen must explicitly say QR is ready or being finalized for My Page visibility |
| Primary follow-up | Completion surface should prioritize `QR 티켓 보기` or equivalent direct route to the user ticket |
| Secondary follow-up | Keep reservation-history access and home return as secondary actions |
| D-1 email notice | Show that the QR email will be sent again 24 hours before the event |
| Delayed QR | If QR generation lags after payment confirmation, show a non-destructive pending state with refresh/retry guidance |

QR rules:

- QR availability is part of payment success reassurance, not a hidden My Page-only fact.
- Do not display field-scan wording, duplicate-scan warnings, or offline validation messaging in Phase 24.

## Accessibility And Readability

| Area | Contract |
|------|----------|
| Keyboard | Queue retry, floor selector, seat summary actions, refund preview, and QR follow-up must all be keyboard reachable |
| Focus | Use existing semantic focus ring tokens; never suppress focus outlines on booking controls |
| Screen reader | Queue state changes, timeout alerts, and refund failures must use live regions or `role="alert"` where appropriate |
| Color contrast | Body text on white uses `#1A1A2E`; muted text uses `#6B6B7B` only on very light backgrounds |
| Touch target | New or touched mobile controls must be at least `44px` |
| Motion | Respect `prefers-reduced-motion`; no flashing or shaking urgency patterns |
| Seat state legibility | Selected, locked, sold, and available states need both color and textual/structural reinforcement in the summary or legend |
| Locale safety | Korean, English, Thai, Simplified Chinese, and Traditional Chinese strings must remain readable without horizontal clipping at `320px` width |

Source: Phase 23 accessibility baseline, current booking timer/seat map patterns, and Phase 24 context decisions.
