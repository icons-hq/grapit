## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| web/API -> database schema | Untrusted booking, payment, and refund state becomes durable production data here. |
| provider webhook -> payment state storage | External provider events can replay or arrive out of order. |
| admin/event config -> booking enforcement | Operator-configured floor and policy data can affect user lock/payment behavior. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-24-01 | T | `seat_maps`, `seat_inventories` | mitigate | Use `floorKey + seatKey` composite identity and contract tests so same visible seat labels on different floors cannot collide (Task 1, Task 2). |
| T-24-02 | T/R | `payments`, `payment_webhook_events`, `refunds` | mitigate | Add explicit async/refund state columns and a dedicated webhook idempotency table so retries cannot double-apply payment/refund state (Task 2). |
| T-24-03 | E | `booking_policies` | mitigate | Persist per-event ticket/payment/cancel policy server-side so later booking/payment logic never trusts client-only limits or disclaimer state (Task 2). |
| T-24-04 | D | migration SQL | mitigate | Gate the migration with expand-only SQL review and the exact Drizzle generate/migrate commands before any verification claim (Task 3). |
</threat_model>
