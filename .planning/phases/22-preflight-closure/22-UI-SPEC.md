# Phase 22 — UI Design Contract

> Visual and interaction contract for Phase 22 Preflight Closure. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase UI Boundary

Phase 22 is a launch-readiness/preflight closure phase for `PREF-01`, `PREF-02`, and `PREF-03`. It must not introduce a new marketing surface, fanmeet product page, landing page, booking/payment feature, global SMS UI, multinational consent UI, or new admin console module.

Default contract: no new user-facing UI. If execution must touch an operator/admin-facing evidence workflow to close SMS, email, legal, validation backfill, or hardening evidence, reuse the existing Grabit admin and shadcn conventions below.

Allowed touched surfaces:

| Surface | Contract |
|---------|----------|
| Evidence ledger docs | Markdown tables and checklist sections only; clear evidence paths and redaction notes |
| Operator/admin evidence view, if already present or directly required | Existing `/admin` layout, shadcn UI components, restrained operational table/card layout |
| SMS/email/legal shipped surfaces, only when a failed gate requires a direct fix | Preserve existing user flow and copy hierarchy; do not restyle beyond the failed behavior |

Blocked surfaces:

| Surface | Reason |
|---------|--------|
| New public landing or fanmeet marketing page | Phase 23+ scope |
| New booking/payment/queue UI | Phase 24+ scope |
| New full admin operations console scope | Phase 25 scope |
| New visual language, decorative hero, gradients, or campaign branding | Phase 22 is operational closure, not acquisition |

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline status/icon spacing |
| sm | 8px | Compact table cell gaps, badge/icon gap |
| md | 16px | Default form, table, and section internal spacing |
| lg | 24px | Evidence group spacing, admin card padding |
| xl | 32px | Admin page padding and major content gaps |
| 2xl | 48px | Large empty state vertical padding |
| 3xl | 64px | Page-level spacing only; avoid in Phase 22 unless reusing existing layout |

Exceptions:

- Interactive targets introduced or touched in Phase 22 must be at least `44px` high/wide on mobile and keyboard reachable on desktop.
- Existing shadcn component internals may keep their current dimensions when the component is not otherwise modified.
- Evidence markdown tables should prioritize readability over visual density; keep one blank line around major sections.

## Typography

Use exactly these sizes for any Phase 22 UI or evidence document headings. Do not introduce additional font sizes.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Source: existing `--text-caption: 14px`, `--text-heading: 20px`, `--text-display: 28px`, `text-base`, and admin page patterns.

Readability rules:

- Evidence docs use short operational headings, not marketing copy.
- Long evidence paths, IDs, log selectors, and URLs must be monospace and may wrap.
- Do not use all-caps Korean labels. English gate statuses must remain exact uppercase values: `PASS`, `ACCEPTED_RISK`, `BLOCKER`, `COMPLETE`, `ACCEPTED_CAVEAT`.
- Existing component internals may retain current `font-medium` classes when not touched; new Phase 22 text uses only 400 or 600.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Main background, table/card surfaces |
| Secondary (30%) | `#F5F5F7` | Admin page background, muted headers, table header bands |
| Accent (10%) | `#6C3CE0` | Primary action, focus ring, active admin navigation, source links only |
| Destructive | `#C62828` | Destructive actions and `BLOCKER` state only |

Accent reserved for: primary CTA, focus ring, active admin navigation, selected tab, evidence source link. Accent must not be used to mean `PASS`, warning, or blocker.

Evidence status colors:

| Status | Surface | Text | Contract |
|--------|---------|------|----------|
| `PASS` / `COMPLETE` | `#F0FDF4` | `#15803D` | Completed direct evidence only |
| `ACCEPTED_RISK` / `ACCEPTED_CAVEAT` | `#FFFBEB` | `#8B6306` | Explicit caveat or maintainer/operator accepted risk; never green |
| `BLOCKER` | `#FEF2F2` | `#C62828` | Launch path can break or evidence is missing/failing |
| Informational | `#F3EFFF` | `#6C3CE0` | Evidence source, traceability, or neutral note only |

Status must not rely on color alone. Every visual status requires the exact text label and, where useful, an icon from lucide.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `증거 저장` |
| Empty state heading | `아직 기록된 증거가 없습니다` |
| Empty state body | `SMS, email, legal gate 실행 후 redacted evidence path와 상태를 기록하세요.` |
| Error state | `증거를 불러오지 못했습니다. 새로고침 후 다시 시도하고, 반복되면 BLOCKER로 기록하세요.` |
| Destructive confirmation | `증거 기록 삭제`: `이 증거 기록을 삭제할까요? 삭제하면 복구할 수 없습니다.` |

Copy rules:

- Status values must be exact: `PASS`, `ACCEPTED_RISK`, `BLOCKER`; validation backfill values must be exact: `COMPLETE`, `ACCEPTED_CAVEAT`, `BLOCKER`.
- `ACCEPTED_RISK` copy must include both approvals: maintainer technical risk and operator business launch risk.
- Evidence copy must say what was checked, when it was checked in KST, where sanitized evidence lives, and what remains next.
- Never include raw OTPs, raw phone numbers, reset links, reset tokens, email secrets, Cloud Run secrets, or unredacted personal data.

## Evidence Presentation Contract

Evidence ledger and any admin/operator evidence view must use this table shape:

| Column | Required Content |
|--------|------------------|
| Gate | `SMS`, `Email`, `Legal`, `Validation Backfill`, or `Hardening` |
| Requirement | `PREF-01`, `PREF-02`, or `PREF-03` |
| Status | Exact allowed status label |
| Evidence | Relative file path, log query, screenshot path, or Sentry/Cloud Run reference after redaction |
| Checked At | KST timestamp |
| Owner | Maintainer, operator, or named role |
| Risk / Caveat | Required for `ACCEPTED_RISK` and `ACCEPTED_CAVEAT`; use `-` for clean `PASS` |
| Next Action | Required for `BLOCKER`; otherwise `-` |

Evidence group ordering:

1. SMS real-device gate
2. Email inbox/reset-to-login gate
3. Legal public/sign-off gate
4. v1.1 validation backfill baseline
5. Operational hardening register

Status display rules:

- `PASS` requires direct evidence and may use `CheckCircle2`.
- `ACCEPTED_RISK` must use warning color and must show maintainer/operator approval date.
- `BLOCKER` must use destructive color and must show owner plus next action.
- Do not collapse `ACCEPTED_RISK` into success copy or success color.
- Missing human/operator evidence is never presented as automated proof.

## Interaction Contract

No new interaction is required by default.

If an operator/admin evidence view is touched:

- Use existing admin layout: left sidebar on desktop, top header, `bg-[#F5F5F7]` main area, white table/card surfaces.
- Keep evidence workflow table-first. Summary cards are allowed only for counts such as `PASS`, `ACCEPTED_RISK`, and `BLOCKER`.
- Row activation must work by click, `Enter`, and `Space`, matching existing `AdminBookingTable` behavior.
- Loading state uses `Skeleton` rows with stable height.
- Empty state appears inside the table body, centered with heading and body copy from this spec.
- Error state uses `role="alert"` and offers an explicit retry or blocker-recording path.
- Destructive evidence deletion is not part of Phase 22. If an existing delete action is touched, it must use `AlertDialog` and the destructive copy above.

If shipped SMS/email/legal surfaces are touched because a gate fails:

- Preserve current layout and user journey.
- SMS verification error text must keep wrong-code, expired/resend, and system-error messages distinguishable.
- Email reset flow must not stop at receipt; copy and states must support reset confirm then login verification.
- Legal route/footer/dialog checks must not introduce new legal marketing copy or multinational consent copy.

## Accessibility And Readability

| Area | Contract |
|------|----------|
| Keyboard | All interactive evidence controls must be reachable and operable by keyboard |
| Focus | Use existing `focus-visible:ring-ring` / `focus-visible:ring-primary`; do not suppress focus outlines |
| Screen reader status | Errors use `role="alert"`; long-running evidence checks use `aria-live="polite"` |
| Color contrast | Body text on white uses `#1A1A2E`; muted text uses `#6B6B7B` only on white or very light surfaces |
| Touch target | New/touched mobile controls must be at least `44px` |
| Motion | Respect `prefers-reduced-motion`; no new decorative motion in Phase 22 |
| Tables | Headers use `scope="col"` when implemented in UI; horizontal overflow is allowed for dense evidence data |
| Redaction | Visual evidence screenshots/docs must mask phone, email, OTP, reset link, token, and secret values |
