# Phase 27 — UI Design Contract

> Visual and interaction contract for Phase 27 Event Operations + Settlement. Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.

---

## Phase UI Boundary

Phase 27 closes the real event-day loop: buyer-visible scannable QR tickets, scanner-only staff check-in, offline pending scan sync, field monitor, event-day playbook actions, settlement/export dashboard, and post-event evidence handoff. It must extend the existing Grabit buyer ticket cards and admin operations shell without creating a native app, scanner hardware workflow, external accounting integration, or admin retrospective product.

Allowed touched surfaces:

| Surface | Contract |
|---------|----------|
| Buyer QR ticket cards | Payment complete and My Page reservation detail render a real scannable QR image plus minimal ticket metadata |
| QR check-in route | Phone-camera QR opens a protected Grabit check-in page; login returns to the intended ticket page |
| Scanner-only staff UI | Mobile-first route for ticket verification, manual `입장 처리`, pending offline attempts, and sync results |
| Field monitor | KPI-first admin monitor for entered/not-entered rate, duplicate/rejected scans, offline backlog, and abnormal alerts |
| Event-day playbook actions | Operational scenario cards for forced refund, weather/facility/cast issue, on-site refund, and exchange handling |
| Settlement/export dashboard | Admin/finance dashboard plus CSV exports for entry status, no-show, reservation/payment/refund summary, and accounting inputs |
| Retrospective handoff | Link evidence to `27-RETROSPECTIVE.md`; do not build a retrospective management UI |

Blocked surfaces:

| Surface | Reason |
|---------|--------|
| Dedicated scanner hardware or native scanner app | Explicitly out of scope; staff use normal mobile phones |
| Automatic check-in on QR page open | D-12/D-13 require review first, then manual `입장 처리` |
| Full admin shell for scanner-only accounts | Scanner-only accounts must not see unrelated admin sidebar/routes |
| External accounting/tax/PG settlement integration | Phase 27 exports inputs only |
| Raw QR token/JTI text display | QR token may exist in the QR URL, but raw token/JTI must not be printed as visible text |
| Admin retrospective product UI | Retrospective is a GSD artifact for this phase |

Source: `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`, `.planning/phases/27-event-operations-settlement/27-CONTEXT.md`, `apps/web/components.json`, `apps/web/app/globals.css`, current `apps/web/app/admin/*`, `apps/web/components/admin/*`, and prior Phase 25/26 UI contracts.

## Layout Contract

### Buyer QR Layout

| Area | Contract |
|------|----------|
| QR card position | Place the QR ticket card immediately after reservation identity/payment success context and before secondary navigation CTAs |
| QR image area | Stable square with white background, visible quiet zone, no overlay text or icons inside the QR image |
| Metadata | Show reservation number, performance title, showtime, seat(s), ticket status, and guidance only |
| Hidden data | Do not show raw QR token, raw JTI, raw JWT/HMAC payload, or full URL text |
| Failure state | If QR image generation fails, keep metadata visible and show a retry button; do not expose raw token as fallback text |

### Scanner-Only Layout

| Area | Contract |
|------|----------|
| Shell | Use a minimal mobile-first scanner shell, not the full admin sidebar |
| Header | Show event/showtime scope, scanner account name, connectivity state, and pending offline count |
| Result band | First visible block is the server verification result: `입장 가능`, `입장 처리 완료`, `이미 사용됨`, `환불/취소됨`, `위조 또는 확인 불가`, `오프라인 대기` |
| Ticket identity | Show reservation number, performance title, showtime, seat(s), and status after result band |
| Primary action | Sticky bottom action area with one primary `입장 처리` button only when the ticket is server-verified as processable |
| Post-action | After success, replace primary action with `입장 처리 완료` state and disable repeat processing |

### Admin Operations Layout

| Area | Contract |
|------|----------|
| Sidebar | Full admin/finance may see `현장 모니터` and `정산·내보내기` under 운영; scanner-only must not see the admin sidebar |
| Page title row | Title left, manual refresh/export CTA right, filters below |
| First screen | Field monitor first screen must answer whether entry is proceeding normally without opening a raw log table |
| KPI grid | 4-8 compact stat cards before drill-down tables |
| Drill-down | Scan logs and export rows are secondary; desktop uses table plus detail pane, mobile uses stacked cards plus full-height sheet/dialog |
| Sticky actions | Sensitive actions stay disabled until required filters/reason are present and must name the blocking requirement |

### Information Order

1. Operational state or risk.
2. Event/showtime/ticket identity.
3. Required next action.
4. Evidence freshness, timestamp, and actor.
5. Secondary metadata such as device, sync state, payment/refund summary, or export filter.

The first screen of every Phase 27 operational surface must show what needs attention now. Do not force operators to inspect raw logs to find duplicate spikes, rejected scans, offline backlog, or settlement export gaps.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Inline icon gaps, compact badge padding, QR metadata dividers |
| sm | 8px | Filter-control gaps, scanner metadata rows, dialog footer button gaps |
| md | 16px | Default card padding, scanner result sections, form spacing |
| lg | 24px | Page-section separation, QR card groups, monitor detail panes |
| xl | 32px | Major dashboard gaps and settlement section breaks |
| 2xl | 48px | Empty states, buyer QR completion spacing, large offline recovery blocks |
| 3xl | 64px | Page-level top/bottom spacing only |

Exceptions:

- New or touched mobile controls must be at least `44px` high or wide.
- Scanner primary action `입장 처리` must be at least `56px` high on mobile and full width in the sticky action area.
- Buyer QR image area must be at least `200px` square on mobile and `220px` square on desktop/tablet, with stable dimensions before generation completes.
- QR cards must include at least `16px` internal padding around the QR image so the quiet zone is not visually crowded.
- Dense admin table cells may use `8px` vertical padding only if the clickable row target remains at least `44px`.
- Status badges may use compact `4px/8px` padding but must not be the only click target.
- Sticky scanner/admin footers must preserve `16px` vertical padding and must not cover validation, warning, or offline sync copy.

Source: `apps/web/app/globals.css`, current admin density, and Phase 25/26 UI contracts.

## Typography

Use exactly these four roles for new or touched Phase 27 UI. Do not introduce a new display scale.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.4 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Readability rules:

- Use `Display` only for top-level page titles and the primary scanner result label when the route is mobile-first.
- Use `Heading` for QR card titles, selected ticket detail titles, monitor section titles, and modal titles.
- Use `Label` for status badges, KPI labels, table headers, event/showtime metadata, evidence timestamps, and buttons.
- Use `Body` for buyer guidance, rejection reasons, offline sync explanations, playbook instructions, and export warnings.
- New authored text uses only weights `400` and `600`.
- Ticket state, rejected scan, offline pending, forced refund, exchange, settlement, and raw export copy must never drop below `14px`.
- Reservation numbers, short event IDs, redacted token references, and export filenames may use UI monospace only at `14px` or `16px`.

Source: inherited core scale from Phase 23/24/25/26 and confirmed by `apps/web/app/globals.css`.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Buyer QR cards, scanner cards, admin cards, dialogs, tables, detail panes, sidebar/header surfaces |
| Secondary (30%) | `#F5F5F7` | Workspace background, table headers, muted evidence bands, disabled/pending metadata, scanner shell background |
| Accent (10%) | `#6C3CE0` | Primary CTA, focus ring, active tab/filter, selected row, QR follow-up CTA, scanner valid action emphasis |
| Destructive | `#C62828` | Rejected/tampered/refunded scan, duplicate already-used warning, destructive confirmations, forced refund, blocking settlement/export warnings |

Accent reserved for: `입장 처리` when the server result is processable, primary QR follow-up CTA, active sidebar item, selected monitor/export row, selected tab/filter, focus ring, and manual refresh/export primary CTA. Accent must not be used for duplicate, rejected, tampered, refunded, cancelled, expired, offline backlog, or destructive finance actions.

Phase-specific state colors:

| State | Surface | Text | Usage |
|-------|---------|------|-------|
| Valid / processed / synced | `#F0FDF4` | `#15803D` | Server-verified entry allowed, completed check-in, synced offline attempt, healthy monitor |
| Warning / pending / offline | `#FFFBEB` | `#8B6306` | Offline pending, sync backlog, stale monitor data, playbook caution, export review needed |
| Error / rejected / duplicate / tampered | `#FEF2F2` | `#C62828` | Duplicate scan, refunded/cancelled attempt, tampered token, wrong showtime, sync failure |
| Informational / selected | `#F3EFFF` | `#6C3CE0` | Selected ticket row, QR guidance, neutral scanner instructions, export filter summary |
| Neutral inactive / disabled | `#F5F5F7` | `#6B6B7B` | No scans yet, disabled actions, unavailable export, archived evidence |

Color rules:

- Status must never rely on color alone. Every badge, result band, row highlight, or KPI card must include exact Korean state text.
- A locally stored offline scan is never green until server sync succeeds.
- Duplicate/already-used outcomes are red or amber only when paired with prior scan timestamp/context where safe.
- Settlement/export summaries use green only for completed export/sync evidence, not for unreviewed accounting readiness.
- Provider-native Toss or browser-native camera/login UI keeps provider/browser styling where applicable.

Source: `apps/web/app/globals.css`, Phase 27 D-01 through D-34, and existing admin state chips.

## Surface Interaction Contract

### Buyer QR Ticket Surface

| Interaction | Contract |
|-------------|----------|
| QR rendering | Render a real QR code image/canvas/SVG from the protected HTTPS ticket URL; metadata-only QR cards are not sufficient |
| QR content | QR payload is an HTTPS Grabit URL that resolves to the protected check-in/management route |
| Metadata | Show only reservation number, performance title, showtime, seats, ticket status, and QR guidance |
| Token visibility | Do not render raw token, raw JTI, JWT payload, or full deep-link URL as text |
| Invalid states | Keep QR visible for buyer context when needed, but show status honestly; scanner verification decides final entry |
| Image failure | Show retry and My Page fallback; never print the token as fallback |

Buyer QR rules:

- QR card must be scannable on a phone camera from normal handheld distance.
- QR image must not shift layout when generated; reserve the square area before load completes.
- If a text link is needed for accessibility, label it as `티켓 검표 페이지 열기` without showing the raw URL.
- Keep buyer QR content calm and short; do not show duplicate/tamper/offline scanner logic on buyer pages.

### Scanner-Only Check-In Flow

| Interaction | Contract |
|-------------|----------|
| Route entry | Opening a QR URL never marks a ticket as used |
| Auth routing | Logged-out visitors go to login and return to the intended ticket page |
| Access denied | Normal member accounts see explicit access denied with login/home actions |
| Verification | Server result is shown before any check-in action |
| Manual action | `입장 처리` appears only for server-verified processable tickets |
| Duplicate result | Show already-used/duplicate result with prior scan timestamp and staff/device context where safe |
| Rejected result | Tampered, refunded/cancelled, expired, wrong-showtime, and already-used states disable `입장 처리` |
| Completion | Successful processing replaces the action with completed state and writes audit evidence |

Scanner rules:

- Scanner-only accounts may use only event/showtime-scoped scan pages, scan/check-in APIs, offline sync, and scan audit evidence.
- Scanner-only accounts must not see refund, reservation management, user management, content, security, settlement, or raw export actions.
- Full admin users may manage scanner-only staff permissions, but the scanner UI itself stays minimal and mobile-first.
- Toasts are allowed only after completed save/sync; the verification result must be visible inline and not toast-only.

### Offline Fallback Sync

| Interaction | Contract |
|-------------|----------|
| Default behavior | Online-first server verification and processing whenever connectivity exists |
| Failure handling | If authenticated scanner session exists and network processing fails, store a local pending scan attempt |
| Local state | Pending item shows attempt time, event/showtime scope, ticket reference, and device-local attempt id without raw PII |
| Sync action | Scanner can run `보류 스캔 동기화` when connectivity recovers |
| Conflict resolution | Server resolves duplicate, tampered, refunded, expired, and already-used outcomes |
| Result visibility | Scanner and field monitor both show pending, synced, and rejected counts/results |

Offline rules:

- Local pending scan data must avoid raw PII and must not expose raw token/JTI in visible UI.
- Local pending is amber/warning, never green.
- If pending queue exists, show a visible banner on the scanner shell before the current ticket detail.
- Sync failures need a clear retry path and must remain visible until resolved or intentionally discarded by an authorized full admin path.

### Field Monitor

| Interaction | Contract |
|-------------|----------|
| Default surface | KPI grid first, logs second |
| Required KPIs | Entered count, not-entered count, entry rate, duplicate scans, rejected scans, offline pending count, offline synced count, latest abnormal alerts |
| Refresh | Auto-refresh every 10 seconds while visible, plus manual refresh CTA |
| Alerts | Duplicate spike, rejected/tampered attempts, refunded/cancelled attempts, offline pending backlog, and sync failures pin above raw logs |
| Drill-down | Row click opens selected alert/scan detail; mobile uses sheet/dialog |
| Empty state | No scans yet is neutral, not success |

Monitor rules:

- The first screen must answer `입장 흐름이 정상인가?`
- Logs are searchable/filterable by event, showtime, scan result, offline state, scanner account, and time range.
- Abnormal alerts must include timestamp, count or threshold, affected showtime, and next action.
- Do not dump raw token, raw PII, or full user-agent strings into the monitor table.

### Event-Day Playbooks

| Interaction | Contract |
|-------------|----------|
| Scenario cards | Forced refund, weather, facility, cast issue, on-site refund, and exchange scenarios are visible as operational cards |
| Card content | Each card shows severity, affected scope, external contact, console action link, and evidence requirement |
| Action dialog | Sensitive actions require reason, target summary, and confirmation before submission |
| External contacts | Show contact label and channel, not private secret values |
| Completion | Completed actions write audit evidence and link back to monitor/settlement context |

Playbook rules:

- Use action-oriented copy; do not turn playbooks into long static documentation pages inside the UI.
- Forced refund and exchange actions must show financial/entry impact before confirmation.
- Weather/facility/cast issue cards can link to notices/support workflows but must not auto-publish public copy without existing admin controls.

### Settlement And Export

| Interaction | Contract |
|-------------|----------|
| Dashboard summary | Show event-level sales, payment, refund, entry, no-show, and export readiness summary |
| Tabs | Use `요약`, `입장/노쇼`, `결제/환불`, `내보내기` as the maximum tab set |
| Filters | Event, showtime, date range, payment method, reservation status, entry status, refund status |
| Exports | Entry status, no-show reservation list, reservation/payment/refund summary, and settlement/accounting input CSV |
| Sensitive export | Requires confirmation with filter summary, reason, actor, and audit note |
| Access | Settlement/export is full admin or finance-capability scope only; scanner-only has no access |

Settlement rules:

- CSV-only output is insufficient; show a dashboard summary before export.
- Export buttons stay disabled until required event/showtime/date filters are present.
- Export filename must include event/showtime scope and generated date, not raw buyer names.
- Raw PII rows should never be previewed in the browser. Show counts, filters, and masked sample metadata only.
- External accounting/tax/PG settlement mapping remains out of scope; label exports as `정산 입력 자료`, not completed accounting settlement.

### Retrospective Evidence

| Interaction | Contract |
|-------------|----------|
| UI scope | No admin retrospective editor in Phase 27 |
| Evidence link | Monitor/settlement surfaces may link to evidence artifacts or show `27-RETROSPECTIVE.md` handoff copy |
| Required evidence | Incidents, non-incidents, improvements, next-event carry-forward, field scan/offline/settlement evidence, and v2.0 completion evidence |

Retrospective rules:

- Do not add forms, workflow states, or approval queues for retrospective input.
- The UI can expose evidence export/link affordances, but the artifact remains the retrospective source of truth.
