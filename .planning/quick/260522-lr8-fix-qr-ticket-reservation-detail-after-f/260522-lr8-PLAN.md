# Quick Task 260522-lr8: Fix QR ticket reservation detail after field check-in

## Goal

After a field staff check-in consumes a QR ticket, customer reservation detail must still load normally and show the QR ticket as used/entered instead of failing with HTTP 409.

## Tasks

1. Separate QR ticket read behavior from QR issuance behavior.
   - Files: `apps/api/src/modules/ticket/qr-ticket.service.ts`, `apps/api/src/modules/reservation/reservation.service.ts`
   - Action: Add a read-safe ticket method that returns existing non-active tickets without throwing, while preserving self-healing issuance when no ticket exists.
   - Verify: Confirm `getReservationDetail()` no longer calls the active-only issuance path for already-used tickets.
   - Done: Used tickets return `qrTicket.status = USED` with no reusable token.

2. Preserve scanner state semantics for already-used tickets.
   - Files: `apps/api/src/modules/ticket/qr-ticket.service.ts`, `apps/api/src/modules/field-operations/field-check-in.service.ts`
   - Action: Let scanner contract decode valid QR tokens and report persisted ticket status instead of collapsing non-active tickets into tampered.
   - Verify: Already-used tickets classify as `already_used`.
   - Done: Re-scans are denied as duplicate/already-used, not treated as malformed tokens.

3. Add focused regression tests.
   - Files: `apps/api/src/modules/reservation/reservation.service.spec.ts`, `apps/api/src/modules/ticket/qr-ticket.service.spec.ts`
   - Action: Cover reservation detail after used QR and scanner contract for used status.
   - Verify: Run targeted API tests for reservation and QR ticket services.
   - Done: Tests pass without touching unrelated dirty web files.
