<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> email availability endpoint | Anonymous user-controlled email input crosses into the auth API. |
| OAuth provider -> social callback | Provider profile data controls social account lookup and registration-token creation. |
| Browser -> social completion endpoint | Untrusted completion form data and phone verification token cross into account creation. |
| Email link -> verification endpoint | Opaque token from an email link updates `users.isEmailVerified`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-260516-vf0-01 | I | `GET /auth/email-availability` | mitigate | Return only `{ available: boolean }`; do not return user ids, providers, phone, verification state, or token data; apply throttle because duplicate checking is intentionally public. |
| T-260516-vf0-02 | S | `findOrCreateSocialUser()` | mitigate | Require `isEmailVerified=true` before issuing tokens for existing social links; otherwise issue email verification and return pending state. |
| T-260516-vf0-03 | E | `completeSocialRegistration()` and controller cookie handling | mitigate | Return pending email-verification response for new social users and set refresh cookie only for authenticated responses. |
| T-260516-vf0-04 | T | `/auth/callback` query params | mitigate | Use query params only to select pending UI and render an encoded email string; never treat query status as authentication and never call `setAuth()` from pending status. |
| T-260516-vf0-05 | R | Email verification resend/request | accept | Existing email-verification token table and latest-token-wins behavior already audit issuance enough for this quick task; no schema change is required. |
</threat_model>
