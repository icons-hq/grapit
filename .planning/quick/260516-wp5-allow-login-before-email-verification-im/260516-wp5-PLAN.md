<interfaces>
Existing contracts to preserve:
- `AuthService.validateUser(email, password): Promise<ValidatedUser>` is called by `LocalStrategy.validate`.
- `AuthController.login` returns `{ accessToken, user, deviceLimitNotice? }` and sets the refresh cookie.
- `UserProfile` currently exposes `isPhoneVerified`; this plan adds `isEmailVerified` to the same profile object and keeps `isPhoneVerified` unchanged.
- `JwtStrategy.validate` already loads the DB user. Extend the returned request user object with current `isEmailVerified` and `isPhoneVerified`; do not trust JWT payload for verification freshness.
- `BookingService.lockSeat(actorOrUserId, showtimeId, seatId)` and `ReservationService.prepareReservation/confirmAndCreateReservation` already accept `string | BookingActor`; extend `BookingActor` with optional verification flags and make controllers pass flags from `req.user`.
- `EmailVerificationStatus` already supports `requestOnMount` and resend behavior when `email` is provided.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client to auth API | Login request body is untrusted but credential validation remains server-side. |
| JWT to request user context | Token proves session, but verification flags must be refreshed from DB by `JwtStrategy`. |
| client to booking/payment API | Booking and payment mutation requests are untrusted and can bypass UI guards. |
| app to Toss Payments | Payment confirm is an external side effect and must not run before verification gates pass. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-Q260516-WP5-01 | S | `JwtStrategy.validate` | mitigate | Load verification flags from `UserRepository.findById` and return them on `req.user`; do not rely on client or JWT payload verification claims. |
| T-Q260516-WP5-02 | E | `BookingService.lockSeat` | mitigate | Reject unverified actors before Redis lock creation and before seat status broadcast. |
| T-Q260516-WP5-03 | E | `ReservationService.prepareReservation` | mitigate | Reject unverified actors before consent capture, pending reservation insert, and seat lock assertions. |
| T-Q260516-WP5-04 | E | `ReservationService.confirmAndCreateReservation` | mitigate | Reject unverified actors before payment-confirm lock and Toss `confirmPayment`. |
| T-Q260516-WP5-05 | I | `LoginForm` and `verify-email` query | mitigate | Put only the user email in the verification query, encode it, and never expose raw verification tokens except the existing opaque token flow. |
</threat_model>
