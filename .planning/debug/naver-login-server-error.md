# Debug Session: naver-login-server-error

## Symptoms

- expected: 네이버 OAuth 로그인 또는 소셜 회원가입 completion flow가 정상 진행된다.
- actual: `https://heygrabit.com/auth/callback?error=server_error&provider=naver` 로 이동하고 오류 페이지만 표시된다.
- error_messages: frontend callback query에 `error=server_error&provider=naver`.
- timeline: 2026-05-18 production에서 현재 재현된다고 보고됨.
- reproduction: production `heygrabit.com`에서 네이버 로그인 시도.

## Current Focus

- hypothesis: production Naver OAuth callback 처리 중 backend provider exchange/profile/session/register path 중 하나가 예외를 던지고 frontend가 generic `server_error`로 표시한다.
- test: repo code path, deployed env, Cloud Run logs, live callback URL behavior를 대조한다.
- expecting: logs 또는 code/env mismatch에서 provider-specific failure evidence가 나온다.
- next_action: gather initial evidence from source, deployment configuration, and production logs.

## Evidence

- 2026-05-18T17:11+09:00: `GET https://api.heygrabit.com/api/v1/auth/social/naver` returns `302` to Naver with `redirect_uri=https://api.heygrabit.com/api/v1/auth/social/naver/callback`; provider console/callback URL mismatch is not the observed failure.
- 2026-05-18T17:09+09:00: Cloud Run logs on `grabit-api-00106-fp6` show `Social callback: provider=naver` and `findOrCreateSocialUser: provider=naver`, followed by `Social user found: userId=4d91a6e9-4da2-472c-ac65-7669b1d1c2ee`.
- 2026-05-18T17:09+09:00: the same callback throws `UnauthorizedException: 연결된 사용자 계정을 찾을 수 없습니다` from `AuthService.findOrCreateSocialUser`, and `AuthController.handleSocialCallback` maps that exception to `/auth/callback?error=server_error&provider=naver`.
- 2026-05-18T17:06:20+09:00: the same Naver provider id successfully authenticated before withdrawal.
- 2026-05-18T17:06:38+09:00: Cloud Run request log shows `POST https://api.heygrabit.com/api/v1/users/me/withdrawal` returned `201`.
- 2026-05-18T17:18+09:00: production DB read-only check shows that Naver `social_accounts` row still points to user `4d91a6e9-4da2-472c-ac65-7669b1d1c2ee`, and that user has `account_status=withdrawn`, `withdrawal_source=self`, `withdrawn_at` present.
- 2026-05-18T17:18+09:00: production `admin_audit_logs` has `action=user.withdraw`, `status=success`, `reason=test`, `created_at=2026-05-18 08:06:38Z` for the same user.

## Eliminated

- hypothesis: Naver client id/secret or callback URL misconfiguration. evidence: OAuth reaches backend callback and yields a Naver provider id before failing in internal account lookup.
- hypothesis: frontend callback page creates the error. evidence: `server_error` is generated by backend `AuthController.handleSocialCallback` catch block.
- hypothesis: new Naver signup path is being reached and failing in phone/signup completion. evidence: logs show `Social user found`, so backend takes the existing social account branch, not `needs_registration`.

## Resolution

- root_cause: self-withdrawal soft-deleted the linked user but kept the `social_accounts` row. Subsequent Naver login matches the existing social row, then rejects the withdrawn user and maps the exception to generic `server_error`, preventing both login and fresh social signup with the same provider identity.
