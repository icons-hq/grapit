# 실운영 준비와 예매 부하 검증 — 2026-11-02

공연·판매 시각은 미정이다. 현장 리허설 담당자는 박상우이며 준비 가능한 실기기는 아이폰이다. 이 기록은 기술 검증 범위와 남은 운영 결정을 구분하며, 공개 오픈 승인으로 사용하지 않는다. [실기기·현장·소액 결제 인수 절차](../runbooks/live-opening-handoff-2026-11-02.md)를 함께 사용한다.

## 운영 준비

- 운영 read-only 점검에서 미래 공연 0개, 진행 중 결제·취소·환불 0개, 미적용 migration 0개를 확인했다. 기존 고객 데이터 17개 테이블을 대조했다. 공연 행의 해시 차이는 조회수 `65123 → 65124` 하나로 설명됐고, 이전 조회수로 재계산한 해시가 원본과 일치했다.
- QR 예약메일의 발송 임대·완료 원장과 복구는 [#243](https://github.com/icons-hq/grapit/pull/243)에 이미 배포됐다. [별도 결제·메일 검증](2026-11-02-payment-automation-verification.md)을 이번 성능 시험의 결과와 혼동하지 않는다.

## 코드와 검증

Queue의 회차 조회, 좌석 잠금·예매 준비의 구매자별 매수 제한 및 좌석 재고 사전 조회를 병합한다. SQL 시작 전에 대기한 요청만 합치고 완료 결과는 저장하지 않는다. 키는 구매자/공연 또는 회차/층/좌석 전체 식별자이며 한 SQL은 최대 128개 키를 처리한다. 단일 요청은 기존 SQL을 사용한다. 누락·중복·잘못된 batch 응답은 거절한다.

요청자 권한·판매 시각·전화번호 동일인 합산·판매/환불 보류/비활성 좌석 판정은 각각 유지한다. 결제 확정의 transaction과 매수 제한 advisory lock은 이 병합을 사용하지 않는다.

- API 단위 166파일·2,730개, typecheck, lint 통과. lint의 기존 경고 50개는 이번 변경 밖이다.
- [CI 41389525751](https://github.com/icons-hq/grapit/actions/runs/41389525751): 실제 PostgreSQL/Valkey 통합 검사, migrations, 브라우저 E2E까지 통과. 로컬 Docker 조회는 API 500으로 실패하여 실제 DB 통합 검사는 CI에서 실행했다.
- 실제 SQL에서 200개 재고 사전 조회가 2회로 병합되는지, 새 판매/환불 보류/비활성 상태를 다시 읽는지, 같은 좌석 번호의 다른 층과 전화번호를 공유하지 않는 다른 국가 계정이 섞이지 않는지 검증했다.

## micro DB에서 600석 끝까지 판매

후보 코드, API 4대 × 2 vCPU/512MiB, pool 2, 입장·좌석 관찰 소켓 각 200개, 방문 1,500명. PG 응답은 300ms 대역이고 승인 요청은 초당 1건으로 나눴다.

- 600석 판매·확정 예매·Ticket Item·QR 각각 600개. 입장 상한 200 이하, 마지막 900명 대기 순서 유지.
- 좌석 갱신 120,000건 수신, 중복 0. 세 묶음의 200개 소켓 모두 결제 종료까지 연결 및 최종 판매 상태 확인.
- 실제 worker 2회가 결제와 겹쳤다. 만료 시험 주문 25개가 실패 상태와 만료 진단 기록으로 정리됐다. 새 좌석 잠금을 해제하지 않았다.
- p95: 잠금 1,135ms, 예매 준비 2,131ms, 승인 완료 554ms, 대기열 진입 2,110ms, 좌석 갱신 1,136ms. **성능 목표 미달**.
- 대기열 상태 요청 37,752건 중 예상하지 않은 오류 17건(503 14건, 플랫폼 429 2건, 전송 시간 초과 1건). 이후 최종 상태는 회복됐지만 오류를 없었던 것으로 처리하지 않는다. 메모리 관측 최대 215MiB.
- 실행 중 8개 프로세스 식별자가 관측됐으나 서비스 상한은 4대였다. 시간에 따른 교체를 8대 동시 예열로 계산하지 않는다.

실행 `grabit-load-launch-20261102-7l7rw`. 앞선 `k82q4` 실행은 만료 주문용 추가 회차가 총 판매 가능 좌석을 늘린 시험 데이터 오류가 있어 최종 매진 판정에서 제외했다. 위 재시험은 같은 회차에 만료 주문을 넣어 수정했다. 단일 발생 프로세스 및 일부 시험의 클라이언트 지연도 보존했으며, 서버 로그와 다른 값으로 섞어 목표 통과를 선언하지 않는다.

## 증설 비교

Cloud SQL `db-custom-1-3840`, API 8대 × 1 vCPU/512MiB, API pool 4, worker pool 2, 입장·좌석 관찰 소켓 300개를 시험했다. 같은 리비전의 API 8개를 관측했고 DB 연결 예산은 `8 × (4 + 1) + (2 + 3) + 5 = 50`으로 실측 가용 97개 이하였다.

실제 worker의 만료 처리가 시작된 뒤 300명이 동시에 승인 요청을 보냈다. 300건은 확정됐으나 p95 잠금 2,060ms·준비 2,224ms·승인 완료 8,337ms로 목표에 못 미쳤다. 추가로 시험의 재요청 8회 중 뒤 4회가 계정별 제한으로 429를 받아 검사가 중단됐다. 실제 호출 제한을 바꾸지 않고 시험 재요청만 기존과 같은 4회로 고쳤다. 실행 `grabit-load-launch-20261102-m46d6`는 **실패**이며 증설 추천의 근거로 쓰지 않는다.

DB `db-custom-4-15360`, API 8대 × 2 vCPU/512MiB에서는 일반 API의 Cloud Run affinity를 분리하고 HTTP·소켓 수신을 각각 4개 작업 스레드로 분산했다. API pool 8, worker pool 2이며 연결 예산 82는 실측 가용 497보다 작다. 각 시험에서 같은 리비전의 8개 프로세스를 예열 후 관측했다. 두 구성 모두 운영에는 적용하지 않았다.

150명 구성은 2026-11-02 06:22:05~06:24:04 UTC에 1,500명이 방문하고 150명씩 네 묶음으로 600석을 끝까지 구매했다. PG 응답은 300ms 대역이며 각 묶음의 승인 요청은 동시에 보냈다. 600개 확정 예매·Ticket Item·QR, 마지막 900명의 WAITING 순서, 입장 상한 150 이하, 좌석 갱신 90,000건과 중복 수신 0을 확인했다. 대기열은 현재 웹의 15~20초 jitter HTTP polling이며 대기열 소켓은 사용하지 않았다. 좌석 소켓은 각 묶음의 승인 완료까지 유지했다. 관측 최대 RSS는 189MiB다.

실제 worker `grabit-worker-launch-20261102-nmqw2`가 06:22:48~06:23:28 UTC에 성공했고, 만료 주문 25개를 정리한 뒤 동시 승인을 시작했다. 승인과 worker 실행이 겹쳤고 새 잠금은 보존됐다. 정상 요청의 예상하지 않은 오류는 0이다. 동일 주문을 의도적으로 동시에 재요청한 검사는 매 묶음 `201/503`을 받고 이후 4회 모두 같은 예매로 `201`을 받았다. 이 예상된 중복 처리 중 응답을 일반 요청의 5xx로 감추거나, 모든 HTTP 응답이 2xx였다고 보고하지 않는다.

증거: [입장 300명](booking-launch-readiness-2026-11-02/300-admission.json), [입장 150명](booking-launch-readiness-2026-11-02/150-admission.json). 실행은 각각 `grabit-load-launch-20261102-2927h`, `grabit-load-launch-20261102-qhvhf`다. 150명 첫 시도 `qzd87`는 시험 도구의 허용 소켓 수 목록에 150이 없어 요청 시작 전에 종료됐으며 성능 표본에서 제외했다. 허용값만 추가하고 재실행했다.

일반 API affinity 분리는 edge 요청에서 `GAESA`만 제거하고 응답에서도 해당 쿠키만 제외한다. Socket.IO polling/upgrade 응답과 인증 쿠키는 보존한다. Edge 회귀 14개, typecheck, production Worker dry-run을 통과했다. 실제 Worker 반영은 GCP 배포와 별도로 기록해야 한다.

운영 증설은 공연 일정·추가 운영비·DB 접속 중단이 가능한 작업 시각을 정한 뒤 수행한다. 사전 백업, 진행 중 주문·환불 및 활성 admission 0 확인, DB 연결 예산 재검사, 승인된 배포와 live smoke, 예열 요청 수·감시 기준 갱신이 필요하다. 적용 후보는 DB 4 vCPU·15GiB, API 8대 × 2 vCPU/512MiB, API pool 8, worker pool 2, admission 150이다. 현재 운영의 micro DB·API 최대 4대·admission 300은 유지했다. 새 구성을 적용하려면 deploy guard의 연결 예산, 최대 인스턴스 및 예열 요청 수를 함께 갱신하고 승인된 배포 경로에서 재검사해야 한다. 결과를 운영의 현행 용량 보장으로 사용하지 않는다.

## 검증 경계와 남은 인수

시험은 예열된 비공개 Cloud Run에서 실행했다. 외부 PG 네트워크·실금전 거래, 공개 edge의 동시 유입/0대 cold start, 비밀번호/OAuth 로그인 폭주, 물리 휴대폰·현장 카메라/통신 복구를 재현한 결과가 아니다. 회원 세션과 인증 guard는 실제 구현을 거쳤지만 합성 계정은 시험 DB에 준비했다.
