# 예매 폭주 지연 개선 — 2026-10-28

현재 운영 소스 `7ff9d8b5655ca7a34648b9311bc15a2c0984391f`와 조회 배치 개선안을 동일한 격리 GCP 환경에서 비교한다. 운영 배포·운영 DB 변경은 이번 작업에 포함하지 않는다. 1,500명 전체 실행에서 주요 폭주 지연이 감소했고 판매 정합성은 통과했다. 전체 지연 SLO는 여전히 미달이다.

후속 요청의 추가 최적화·재검증은 [후속 보고서](booking-burst-latency-followup-2026-10-28.md)에 기록한다. 아래 수치는 첫 번째 실행의 결과를 그대로 보존한다.

## 변경과 원인

JWT 권한 조회, 브라우저 refresh 세션 검증, 공연 판매 상태 확인에서 요청마다 발생하던 PostgreSQL 조회를 `FreshReadBatcher`로 묶었다. 현재 I/O 턴의 요청을 모으고 최대 128개 서로 다른 키를 한 쿼리로 읽는다. 각 reader는 한 쿼리씩 실행하여 기존 5개 연결 풀의 나머지 연결을 다른 작업에 남긴다.

조회 결과는 보관하지 않는다. 쿼리가 시작된 뒤 들어온 요청은 같은 키여도 다음 DB 조회로 처리한다. 탈퇴·병합 계정, 권한 변경, 세션 소유자·만료·폐기, 비공개 공연과 판매 시작·마감 검증을 유지한다. 입장 제한·FIFO·매진 처리 Lua와 좌석 잠금·결제 확인의 트랜잭션은 수정하지 않았다. 스키마 migration도 없다.

실제 PostgreSQL 테스트에서 기존 1,500개 JWT 조회와 1,501개 세션 조회가 각각 24회 이하의 예산을 초과해 실패하는 것을 확인한 뒤 수정했다. 공연 gate 역시 1,502회 조회로 실패하던 사례가 2회 이하 예산으로 통과한다. 테스트는 처리 시간 대신 실제 SELECT 수와 반환된 계정·권한·공연 구분을 검증한다.

[별도 진단](booking-burst-latency-2026-10-28/diagnostic-profile.json)에서는 좌석 잠금 8개, 예매 준비 19개의 SQL 호출과 연결 풀 대기가 확인됐다. 대기열 진입은 Node 핸들러 안의 시간보다 클라이언트와 Cloud Run 요청 로그에서 측정한 시간이 길었다. 따라서 내부 함수 시간만으로 개선을 판정하지 않고 아래 왕복 지연을 사용한다. 이 진단은 200건 동시 결제 확인을 사용했으며, 초당 한 건을 보내는 최종 시나리오와 직접 비교하지 않는다.

## 비교 조건과 격리

- API: 인스턴스당 1 vCPU / 512 MiB, 최대 2개, heap 256 MiB, concurrency 1,000, 애플리케이션 DB 풀 5, 공연별 동시 입장 200. 비교 중 두 인스턴스를 warm 상태로 유지했다.
- PostgreSQL 16: 별도 물리 인스턴스 `grabit-db-burst-20261028`, `db-f1-micro`, SSD 10 GB, 단일 존. 신규 합성 DB에 migration 51개와 동의 기준 데이터 43개를 적용했다.
- Valkey: 별도 `grabit-valkey-burst-20261028`, `CUSTOM_PICO` primary + replica 1개, multi-zone, standalone, `noeviction`.
- 사용자 1,500명은 모두 합성 계정과 서로 다른 인증 전화번호 식별자를 사용한다. 600석을 200명씩 3회 판매하고, 대기 소켓 1,300개·좌석 관찰 소켓 100개를 연다.
- 좌석 선택·예매 준비는 각 200명 구간에서 동시에 요청한다. 결제 확인은 300 ms 모의 PG를 사용해 1초 간격으로 보낸다. 대기 상태 조회 간격은 클라이언트와 같은 15–20초 분산값이다.
- 비공개 IAM API·전용 DB 계정·테스트 서명 키를 사용한다. Background worker와 실제 PG·메일·SMS 등의 외부 자격증명은 제외했다. 실행 guard는 대상 리소스, DB 소유자, 테스트 모드와 만료 시간을 확인한다.
- 기준 이미지의 Node·OS·의존성은 고정하고 개선안의 Nest/SWC 빌드 결과만 교체했다. [소스·이미지·측정 도구 해시](booking-burst-latency-2026-10-28/source.json), [실측 자원 설정](booking-burst-latency-2026-10-28/measured-resource-config.json), [DB 격리 확인](booking-burst-latency-2026-10-28/db-bootstrap-proof.json)을 보관한다.

주요 폭주 경로는 대기열 진입 **37.5%**, 좌석 잠금 **27.8%**, 예매 준비 **47.0%** 감소했다. 반면 좌석 조회는 2,109→2,384 ms로 증가했다. 공개 상세/좌석 조회 개선을 확인했다고 주장하지 않는다.

개선 실행은 653.8초 동안 600석 판매를 완료했다. 확정 예매·판매 좌석·Ticket Item·QR credential은 각각 600개, 최대 동시 입장은 200명, 최종 대기자는 900명이다. 추가 입장 이벤트는 400/400건, 좌석 이벤트는 60,000/60,000건이고 중복 전달은 0건이다. 세 구간의 중복 결제 확인은 모두 같은 예매로 수렴했다. 진행 중 중복 확인에서 예상한 503 여섯 건은 제외하고 **예상 밖 오류는 0건**이다. API 두 프로세스의 관측 최대 RSS는 각각 215 MiB였다.

기준 실행의 대기 상태 조회에는 HTTP 500이 24/37,326건(0.0643%) 있었고 개선 실행은 0/36,894건이었다. 기준 실행 중 프로세스 교체와 오류 원인의 인과관계는 확정하지 않았으므로 코드 변경이 해당 오류를 근본 해결했다고 주장하지 않는다.

정합성·메모리·초당 한 건의 결제 확인 목표는 통과했지만 **전체 지연 SLO는 여전히 미달**이다. 실행 결과는 `capacity_limited`이며 Job도 SLO 미달에 따라 exit 1로 끝났다. [독립 읽기 전용 SQL·Valkey 대조](booking-burst-latency-2026-10-28/optimized-queue-audit.json)도 600개씩의 판매/예매/Ticket Item/QR, 활성 입장 **0명**, WAITING 상태 **900명**으로 통과했다.


[Cloud Monitoring 원본](booking-burst-latency-2026-10-28/rehearsal-final-metrics.json)의 수집 구간에서 컨테이너 메모리 p95 집계의 최대값은 54.9%, Valkey 메모리 사용률은 최대 13.6%, eviction은 0이었다. 집계와 수집 지연이 있는 지표이므로 순간 최고치로 해석하지 않는다.

## 코드 검증

- API 단위 테스트: 161개 파일, 2,688개 통과.
- PostgreSQL/Valkey 통합 테스트: 36개 파일, 432개 통과. 권한·세션·공연 gate의 배치/최신성 회귀 5개와 실제 Valkey Cluster 19개를 포함한다.
- [전체 검증 요약](booking-burst-latency-2026-10-28/validation.json): API typecheck 및 Nest/SWC build 통과. lint 오류 0개, 기존 경고 50개.
- API 공통 배치 단위 테스트는 크기 제한, 키별 분리, 쿼리 도중 들어온 동일 키의 최신 조회, 실패 이후 복구를 확인한다.
- 변경 화면이 없는 API 최적화이므로 별도 브라우저 UI 검증은 실행하지 않았다.

## 해석의 한계

QR 서명 버전이 빠졌거나 초기화 시 동의 기준 데이터가 제거된 사전 실행은 테스트 환경 오류로 제외했다. 두 문제를 수정하고 기준 실행과 개선 실행에 같은 migration·설정을 적용했다. 200명까지만 판매한 진단 실행도 전체 결과에 섞지 않았다.

같은 격리 자원과 시나리오에서 실시한 한 쌍의 전체 실행 비교다. 클라우드 실행 시점의 변동과 인스턴스 교체 영향을 포함하며 통계적 신뢰구간을 입증하는 반복 표본은 아니다. 기준 실행 동안 총 3개 프로세스 ID가 관측됐지만 설정상 최대 인스턴스는 2개였다. 이를 3대 동시 운영으로 해석하지 않는다.

모든 지연 목표를 통과해야 전체 SLO 통과다. 좌석 잠금·좌석 알림 목표는 p95 1초, 다른 측정 경로는 2초다. 주문/좌석/QR 정합성 통과나 빠른 paced 결제 확인만으로 전체 SLO를 통과했다고 보지 않는다.

실제 PG 승인·환불, 비밀번호/OAuth 로그인 폭주, cold start, 공개 edge·브라우저 쿠키, 실제 단말, QR 입장 충돌은 검증 범위 밖이다. 200명이 동시에 결제 확인하는 부하는 최종 초당 한 건 시나리오로 보장하지 않는다. 운영 background worker와 고객 활동이 겹치는 효과도 포함하지 않는다.
