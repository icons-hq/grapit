# NOL 좌석·결제 관찰과 Grabit 예매 개편

2026-10-26. 기존 [티켓 탐색 개편](nol-ticket-redesign-2026-10-26.md)에 이어 실제 좌석 선택, 가격 선택, 예매자 정보, 결제수단 화면을 확인했다. Grabit의 공연장 좌석도 재사용, 구매자 예매 화면, 대기열 순서를 개편하고 로컬에서 검증했다. 운영 배포·운영 DB 변경·실결제·환불·메시지 발송은 하지 않았다.

## 관찰 근거와 범위

사용자가 로그인한 내장 브라우저에서 [엘리자벳 공연](https://nol.yanolja.com/ticket/products/26009314)의 실제 예매 화면을 열었다. 앞서 [헬스키친 공연](https://nol.yanolja.com/ticket/products/26007169)은 Chrome SSO에서 `INVALID_DEVICE_ID`로 중단됐으므로 성공한 좌석 흐름의 근거로 사용하지 않았다.

| 단계 | 직접 확인한 동작 |
| --- | --- |
| `tickets.interpark.com/onestop/seat` | 무대와 여러 층을 포함한 SVG, 등급 색상, 회색 비가용 좌석, 줌·이동, 선택 좌석 요약, 10분 타이머 |
| 선택 완료 | `POST /onestop/api/seats/select`의 201 응답 후 `?step=price`로 이동 |
| 가격 선택 | 선택 좌석의 가격 유형·수량 선택, 일반 가격, 예매 버튼. 관찰한 할인 조건을 Grabit의 실제 상품 정책으로 가정하지 않음 |
| `/onestop/preorder` | 예매자 정보, 수령 방식, 필수 동의. 정보·동의 처리는 사용자가 직접 수행 |
| `/payment/order/:orderId` | 주문 요약과 결제 서비스 연결. 실제 주문 식별자는 기록에서 제외 |
| `nol-payment.yanolja.com/payment` | NOL 머니, 카카오페이, Npay, 기타 결제수단, 총액과 결제 버튼. 데스크톱과 390×844 화면 확인 |

결제 버튼을 누르지 않았다. 뒤로 이동한 뒤 예매 나가기 안내를 통해 공연 상세로 복귀했다. 이 관찰만으로 NOL 서버의 좌석 해제 완료나 내부 결제·락·대기열 구현을 증명하지 않는다.

REA 6.8.0 / Node 24.22.1로 브라우저에 전달된 공개 코드를 분석했다. 좌석·사전 주문은 `onestop-v2-front`, 결제는 별도 `nol-payment` 번들이다. 결과와 공개 소스 URL·해시는 [REA 분석 요약](nol-booking-rebuild-2026-10-26/rea-analysis.json)에 있다.

| 대상 | 수집 / 구문 분석 | 분석 bytes | AST 노드 | 구문 오류 |
| --- | ---: | ---: | ---: | ---: |
| 좌석·사전 주문 | 31 / 12 | 447,287 | 125,341 | 0 |
| 결제 | 15 / 4 | 1,229,887 | 310,269 | 0 |

선택하지 않은 19개·11개 파일은 분석 범위 밖이다. semantic graph는 부분 결과이며 결제 분석은 파일별 노드·unknown 보관 한도에도 도달했다. 정적 route inventory가 비어 있다는 사실을 경로가 없다는 뜻으로 해석하지 않았다. 실제 경로와 클릭 결과는 브라우저 관찰로 확인했다. 원본 번들, 개인 정보, 주문 URL, 쿠키, 결제 화면의 잔액은 저장소에 포함하지 않는다.

재현 명령 형태:

```sh
npx --yes --package=node@24.22.1 --package=rea-agents@6.8.0 \
  rea analyze-javascript-application <captured-script-directory> \
  --source-paths-json <selected-chunks.json> --detail summary \
  --evidence_output <evidence.json> --analysis-timeout-ms 60000 \
  --max-semantic-nodes 300000 --max-semantic-nodes-per-file 40000 --format json
```

## 구현한 계약

### 공연장 좌석도

- `GET /api/v1/admin/venue-layouts?venueName=…`, `GET /:id`, `POST /api/v1/admin/venue-layouts`를 추가했다. `event.write` 권한으로 접근하며 생성은 `venue.layout.create` 감사 로그에 기록한다.
- 같은 공연장·이름으로 저장하면 새 버전을 만든다. 트랜잭션 advisory lock과 기존 유일 키가 동시에 저장된 버전도 분리한다. 원본 버전을 수정하거나 삭제하는 API는 제공하지 않는다.
- 템플릿은 최대 7개 층의 SVG 주소, 좌석 ID, 등급 색상, 구역을 보관한다. 가격은 공연이 정한다. 관리자에서 불러올 때 이름이 같은 기존 등급의 가격을 유지하고, 새 등급은 0원으로 시작하므로 해당 공연의 가격을 확인해야 한다.
- 공연의 `seatMaps[].venueLayoutId`가 특정 버전을 가리킨다. 서버는 공연장·층·SVG·좌석·구역을 대조한 뒤 연결하고, 공연별 등급·가격 배정을 별도로 저장한다. 다른 공연장이나 조작된 좌석 구조는 422로 거절한다.
- 층·구역·좌석 구조를 편집하면 그 공연의 사본으로 분리한다. 새 버전을 저장해도 이전 공연이 가리키는 버전은 바뀌지 않는다. 판매 시작·예매·현장 이력이 있는 공연의 구조 보호는 계속 적용한다.
- 구역은 층 안에서 고유하며, 등록된 좌석을 한 구역에만 배정한다. 구역이 없는 기존 좌석도는 층 전체로 사용할 수 있다. 템플릿은 같은 좌석의 로컬/층 포함 ID 중복과 다른 층 ID를 거절한다.
- 템플릿이 먼저 만든 공연장에는 첫 공연이 주소를 입력할 수 있다. 이미 다른 공연이 사용하는 주소·교통 안내는 기존 보호 규칙을 따른다.
- 관리자 JSON 요청에만 2 MiB 한도를 적용한다. 구매자 API의 기본 한도와 JSON 파싱은 유지한다. 좌석·배정 INSERT를 1,000개씩 나눠 10,000석의 HTTP 저장·공연 연결을 검증했다.

실제 공연장의 정확한 좌석 위치는 운영자가 확인한 SVG와 좌석 ID가 기준이다. 로컬 화면 검증에는 2층 184석 대극장과 72석 스튜디오의 명시적인 검증용 데이터를 사용했다. 이를 실재 공연장의 검증된 도면으로 제공하지 않는다.

### 구매자 예매

- 일정은 한 줄로 표시하고 변경 시 달력·회차 선택을 펼친다. 회차를 바꿀 때 기존 선점을 해제하는 경로를 유지한다.
- 데스크톱은 좌석도와 오른쪽 선택 좌석·가격 패널, 모바일은 지도와 펼칠 수 있는 하단 선택 요약을 사용한다. 4개 언어를 지원한다.
- 층과 구역별 잔여석을 표시한다. 구역 확대는 실제 렌더링된 좌석 경계로 계산한다. 키보드용 좌석 목록도 같은 구역을 필터링한다. 실시간 상태 갱신은 SVG를 다시 파싱하거나 사용자의 줌 위치를 초기화하지 않는다.
- 모바일은 층 전체 보기로 시작하고 구역 선택·줌으로 확대한다. 줌 컨트롤은 지도 안에 겹쳐 표시하며 하단 결제 요약 위로 튀어나오지 않는다.
- Grabit은 클릭 시 즉시 서버 선점을 요청하고, 다음 단계 전 소유권을 재조회한다. NOL에서 관찰한 ‘선택 완료’ 경계와 동일하다고 주장하지 않는다. 충돌·만료·회차 변경의 기존 보상 해제와 결제 복구 경로를 유지한다.
- 결제 화면은 공연·좌석·예매자·동의와 금액·결제수단을 나눠 배치한다. 서버 가격, 주문 재사용, 결제수단 정책, 서버 시각·마감, Ticket Item 단위 QR 계약은 유지한다. NOL의 할인·머니·회원 혜택을 만들지 않는다.

### 대기열 순서

기존에는 ZSET score에 `Date.now()`만 넣어 같은 밀리초의 진입 순서가 UUID 사전순으로 바뀌었다. 고정 시각과 역순 UUID로 재현한 뒤 수정했다.

생성 Lua가 같은 Redis hash slot에서 `max(요청 시각, 직전 순번 + 1, 현재 대기열 꼬리 + 1)`을 배정한다. 실제 진입 시각 `enteredAt`과 정렬 값 `queueOrder`를 분리했다. heartbeat와 인덱스 복구는 기존 순번을 유지한다. 카운터가 만료돼도 남아 있는 대기열 꼬리에서 이어간다. 기존 세션에는 진입 시각을 사용하는 호환 경로가 있다.

같은 밀리초, 서버 간 시계 역행, 카운터 만료, 인덱스 유실·재진입, 동시 200명과 입장 상한을 실제 Valkey에서 확인했다. 이 순서는 Redis가 원자적으로 접수한 순서이며, 서로 다른 기기에서 버튼을 누른 물리적 시각을 보증하는 것은 아니다.

## 부하 결과

아래는 예매 화면 재구성 시점의 측정이다. 이후 운영 반영된 대기열·결제 최적화와 동일 사양 GCP 재검증 결과는 [600석 운영 검증](girl-rules-600-capacity-2026-10-27.md)에 기록했다. 화면·좌석도 개편의 최신 코드 통합 결과는 [2026-10-28 통합 QA](../../design-qa.md#2026-10-28-최신-운영-코드-통합)를 따른다.

[측정 JSON](nol-booking-rebuild-2026-10-26/capacity-result.json)은 수정된 코드로 실행한 최종 전체 측정이다. 아래 명령은 외부 URL·DB를 인자로 받지 않고 일회성 PostgreSQL 16 / Valkey 8 / API를 만든다. 종료 시 이번 시험의 프로세스·컨테이너만 정리했다.

```sh
node scripts/revamp/isolated-capacity.mjs --run \
  --sessions=100,500,1000,1500 --socket-clients=100 \
  --api-instances=2 --db-pool-max=2 --pg-latency-ms=300 \
  --output=/absolute/private/capacity-result.json
```

API 2개, 각 DB pool 2개, HTTP 연결을 미리 열어 둔 동시 요청, Socket.IO 100개, PG 응답 300ms 지연의 로컬 시험이다. 각 단계는 동시에 요청하지만 서로 다른 단계는 순차 실행한다. 기존 로컬 작업·컨테이너가 함께 있는 개발 장비이므로 전용 하드웨어나 운영 용량 결과가 아니다.

| 동시 세션 | 입장 / 대기 | 구매 완료 | 선점 p95 | 결제 확정 p95 | 좌석 알림 전달 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 100 / 0 | 100 | 110ms | 737ms | 10,000 / 10,000 |
| 500 | 500 / 0 | 500 | 435ms | 2,199ms | 50,000 / 50,000 |
| 1,000 | 1,000 / 0 | 1,000 | 805ms | 4,293ms | 100,000 / 100,000 |
| 1,500 | 1,000 / 500 | 1,000 | 864ms | 3,969ms | 100,000 / 100,000 |

총 2,600건의 구매에 대해 판매 좌석·확정 예약·Ticket Item 수가 일치했다. 각 단계의 동일 좌석 경쟁과 동일 QR 입장 경쟁은 승자가 한 명이었다. 두 API에 연결된 클라이언트별 좌석 ID를 대조해 알림 260,000건의 누락·중복이 없음을 확인했다. 별도 잔여석 절반 시나리오에서도 대기 순번이 중복·누락 없이 연속이었다.

같은 주문을 세 번 동시에 확정하면 한 요청이 처리하는 동안 두 요청은 503 재시도 응답을 받았다. 완료 후 두 API에 재요청한 결과 모두 201과 같은 예약 ID를 반환했고 중복 발권은 없었다. 이는 진행 중 재시도 응답을 포함한 검증이며 모든 동시 요청이 즉시 성공한 것은 아니다.

Valkey 중단 시 요청은 타임아웃됐다. 복구 후 재선점은 409였고 `my-locks`에서 동일 소유자의 선점 한 건을 확인했다. 응답을 잃은 첫 요청이 이미 반영된 경우의 정상 복구다. PostgreSQL 중단 후 조회는 200으로 복구했다. 최종 측정의 예상 밖 HTTP 오류·전송 오류는 0건이었다.

지연 기준은 선점·좌석 경쟁·좌석 알림·입장 p95 1초, 나머지 p95 2초, 예상 밖 오류율 1% 미만이다. **100명은 전체 기준 통과, 500명 이상은 지연 기준 미달**이므로 최종 상태는 `capacity_limited`다. 10,000명·20,000명 동시 접속, 운영 Cloud Run/Cloud SQL, cold connection storm, 실제 PG 인증·승인, 실제 모바일 기기는 측정하지 않았다.

초기 시험의 가상 사용자 전화번호 중복, 성공한 구매의 만료된 대기열 세션을 장애 시험에 재사용한 문제, 단계 사이에 오래 쉰 HTTP 연결, 여러 단계에서 같은 사용자의 결제 제한을 누적한 문제를 시험 도구에서 수정했다. 동시 확정 중 503과 완료 후 재시도도 구분했다. 이 과정의 실패를 제품의 중복 판매나 결제 실패로 집계하지 않았다.

## 검증 및 운영 적용

- 실제 HTTP/PostgreSQL: 버전 동시 저장, 이전 공연 보존, 다른 공연장·변조 좌석 거절, 판매 이후 구조 변경 거절, 권한, 구역 중복, 10,000석 저장·연결.
- 실제 Valkey/Cluster 및 PostgreSQL: FIFO, 잠금 소유권·소모, 결제 확정·보상, 늦게 도착한 승인, handoff 해제. 기존 전체 통합 414개와 추가 계약 테스트를 수행했다.
- 브라우저: 두 공연장의 선택·층 이동·구역 줌·모바일 요약·결제 진입·좌석 선택 복귀. 관리자 버전 불러오기 → 구역 편집으로 분리 → 새 버전 → 초안 저장 → 공연 반영 후 API로 가격·버전·원본 보존을 재확인했다.
- 로컬 브라우저에는 실 PG 키를 넣지 않아 결제 위젯의 설정 누락 안내와 비활성 버튼을 확인했다. 실제 PG 승인 화면 대신 API 부하 시험의 명시적인 가상 PG로 준비·확정·발권을 검증했다.
- API·웹 타입 검사, 공유 라이브러리 빌드, 관련 lint, `git diff --check`, frozen lockfile 검증을 통과했다. lint는 오류 0개이며 기존 관리자 이미지·effect 경고 5개가 남는다.
- Next.js production build는 별도 복사본에서 `--webpack`과 기존 Turbopack 설정에 대응하는 Markdown raw loader로 실행해 컴파일·타입 검사·38개 정적 페이지 생성을 통과했다. 실행 중인 기존 개발 서버의 출력은 덮어쓰지 않았다. 실제 배포 CI와 Turbopack production build는 이 검증에 포함하지 않았다.

감사 enum 검증은 새 작업을 빠뜨리지 않도록 갱신했고, migration은 기존 배포의 5초 lock timeout을 유지하도록 고쳤다. [검증 환경·로그 해시](nol-booking-rebuild-2026-10-26/verification.json)를 남긴다.

`0050_venue_layout_templates`는 nullable floor config, template 구분·인덱스와 감사 enum을 추가한다. 기존 공연별 좌석도는 `is_template=false`로 유지되며 자동으로 공유 템플릿이 되지 않는다. 운영 적용은 승인 후 기존 CI/CD로 migration을 먼저 실행하고 API·웹을 함께 배포해야 한다. 새 대기열 순서를 보장하려면 예매 게이트를 닫고 기존 대기·결제 세션을 정리한 뒤 모든 API를 같은 버전으로 전환하고 다시 열어야 한다. 이전 writer와 새 writer가 섞인 상태의 FIFO는 보장하지 않는다. 운영 live smoke와 실제 PG 검증은 아직 수행하지 않았다.
