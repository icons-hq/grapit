소스 변경에서 실제 앱 컴파일은 API 18.6 → 16.3초, Web 46.6 → 51.3초였다. 같은 실험에서 API의 캐시 저장은 61.5초 줄었다. 이 차이를 근거로 빌드 명령은 유지하고 설치 대상과 캐시 저장량을 줄였다.

앱별 설치에는 해당 앱·shared에 필요한 의존성만 포함한다. Web 공개 빌드 인자는 Web 컴파일 직전에 적용한다. `max`는 소스만 바뀌면 설치 레이어를 살릴 수 있다. `min`에서는 새 러너가 중간 설치 레이어를 다시 만들 수 있으므로 그 시간도 측정에 포함했다. 두 이미지의 GHA cache scope와 병렬 빌드 구조는 유지한다. [Docker 캐시 모드](https://docs.docker.com/build/cache/backends/#cache-mode) · [Docker 레이어 순서](https://docs.docker.com/build/cache/optimize/)

ARM64 Docker Desktop에서도 새 빌더로 확인했다. 기존 → 새 Dockerfile의 `max`에서 소스 변경 시 새 캐시 blob은 API 465.0 → 81.9 MiB, Web 438.6 → 72.5 MiB였다. lock을 바꾼 뒤 그 캐시를 다시 읽고 shared와 앱 소스만 바꾸자 API는 `max` 41.0초 / `min` 33.2초, Web은 40.4초 / 31.4초였다. 두 `min` 빌드 모두 설치를 다시 수행했다.

**운영 예상 계산.** 각 운영 기록의 이미지 exporter 시작 전 구간에는 같은 앱·변경 종류의 GitHub 실험에서 확인한 변경 후/전 시간 비율을 적용했다. 실제 푸시 후 남은 캐시 저장 시간에도 실험에서 OCI 출력 완료 후 관측한 변경 후/전 시간 비율을 적용했다. Artifact Registry 푸시, Cloud Run, 마이그레이션과 모든 러너 대기시간은 각 운영 기록에서 가져와 `needs`를 다시 계산했다. 운영 캐시 상태·네트워크·러너 성능에 따라 실측은 달라질 수 있다. 실험 러너 6개의 seed와 대조군까지 포함한 일회성 합계는 43:22였다.
