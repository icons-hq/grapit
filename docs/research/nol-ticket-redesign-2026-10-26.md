# Grabit 티켓 화면 개편 근거 — 2026-10-26

## 범위

사용자 요청에 따라 [REA](https://github.com/morluto/rea)와 로그인된 Chrome으로 [NOL 티켓](https://nol.yanolja.com/ticket)을 조사했다. NOL의 디자인·메뉴·탐색 구조를 기준으로 Grabit을 개편하되 Grabit 이름과 기존 공연 데이터를 유지한다. 사용자는 필요한 데이터 구조 변경도 허용했다. 후속 지시로 색상은 기존 Grabit 보라색 `#6C3CE0`와 중립색 팔레트를 유지한다.

이번 변경은 구매자 웹과 이를 지원하는 카탈로그·관심 공연 API다. 기존 결제·환불·좌석 잠금·대기열·좌석별 QR의 권한 및 동시성 계약은 유지한다. 운영 배포와 운영 DB 변경은 실행하지 않았다.

## REA로 확인한 것과 한계

- Chrome에 실제 로드된 공개 JavaScript 51개를 수집했다. 전체 분석은 vendor 번들 처리 중 제한 시간에 도달했다.
- 티켓 page 및 관련 chunk 2071·3323·6830·8303, 총 5개를 선택해 `rea-agents@6.8.0`과 Node 24.22.1로 분석을 완료했다. 구문 분석 오류는 0개다.
- 분석한 텍스트는 190,092 bytes, AST 노드는 54,056개, 정적 관찰 결과는 284개다. 이 숫자는 기능·API 또는 버그 개수가 아니다.
- 나머지 46개 파일은 분석 범위 밖이다. semantic graph는 파일당 20,000-node 제한에 도달해 `partial`이다. 정적 route inventory만으로 런타임 경로나 비공개 API가 없다고 판단하지 않았다.
- [재현용 분석 요약](nol-ticket-redesign-2026-10-26/rea-analysis.json)에 선택된 공개 소스 URL, 해시, 분석 범위와 한계를 남겼다. 대용량 원본 번들과 세션 자료는 저장소에 포함하지 않았다.

실행한 명령의 형태:

```sh
npx --yes --package=node@24.22.1 --package=rea-agents@6.8.0 \
  rea analyze-javascript-application <captured-script-directory> \
  --source-paths-json <selected-ticket-chunks.json> \
  --detail summary --evidence_output <evidence.json> \
  --analysis-timeout-ms 60000 --format json
```

REA의 정적 결과는 구조 파악에 사용했다. 색상·치수·반응형 배치·실제 클릭 결과는 Chrome 스크린샷과 렌더링된 DOM/계산 스타일로 판단했다. NOL의 백엔드나 전체 사업 기능을 복원했다고 주장하지 않는다.

## 렌더링 근거

홈을 끝까지 확인하고 장르, 랭킹, 오픈 예정, 검색, 상세, 전체 카테고리, 마이페이지의 데스크톱·모바일과 주요 열린 상태를 캡처했다. 비교 기준 CSS viewport는 데스크톱 1440×1000, 모바일 390×844다. localhost의 기존 Chrome 110% 확대는 임시 viewport 보정으로 맞췄으며 사용자 기본 확대 설정은 변경하지 않았다.

| --- | --- |
| Pretendard, 흰 배경, 강조 CTA, 최대 1240px 콘텐츠 | 기존 폰트·레이아웃 반영, 색상은 사용자 지시대로 Grabit shared theme 유지 |
| 홈 72px 헤더·64px 메뉴·400px 배너, 72px 장르 아이콘 | Grabit 검색·계정 메뉴, 실제 배너, 장르 바로가기 |

공개 장르 아이콘 8개는 로컬 PNG로 저장했고 [출처와 SHA-256](../../apps/web/public/images/ticket-genres/sources.json)을 기록했다. NOL 로고·공연 포스터·배너를 Grabit 상품 데이터로 추가하지 않았다. Grabit 공연·배너는 기존 저장소/CDN 주소를 사용한다.

## 데이터와 동작

- 기존 DB enum에 있던 10개 장르를 shared/admin/public 계약에 모두 노출한다. ID·기존 enum 값·기존 예매는 변경하지 않는다.
- 장르가 없는 목록 요청은 전체 장르를 조회한다. 지역·공연장·KST 날짜 겹침·공개 판매 상태를 count와 pagination 이전에 적용한다. 열릴 시각/공연일 정렬, 안정적인 ID 보조 정렬과 필터별 캐시 키를 추가했다.
- 홈과 랭킹·둘러보기에는 종료된 공연도 표시한다. 랭킹은 **누적 조회수**임을 표시한다. 판매 점유율·후기·할인·일간 판매 순위를 만들지 않는다.
- `0049_performance_favorites`는 빈 계정-공연 관계 테이블만 추가한다. 사용자별 최대 200개, 멱등 저장, 동시 요청 상한과 계정 간 분리를 보장한다.
- 최근 본 공연은 기기 내 공개 UUID/조회시각만 최대 24개·30일 보관한다. 사용자가 비울 수 있다.
- 상세에서 고른 `showtimeId`는 로그인/인증 복귀 주소에 유지한다. 해당 공연에 속한 미래 회차만 기존 `changeShowtime` 경로로 적용한다. 좌석 선점은 기존 예매 화면에서만 일어난다.
- 4개 언어, 기존 예매 가능 시간·runtime flag·QR·결제·환불 규칙은 유지한다.

## 검증 환경과 운영 반영

기존 로컬 DB를 복제한 **별도 로컬 DB**에서 migration을 적용했다. 현재 운영의 공개 카탈로그는 종료된 공연 1개이므로 다중 장르·오픈 예정·두 날짜 선택 검증에는 명시적으로 표시한 일회성 로컬 공연 10개와 QA 계정 2개를 사용했다. 후속 색상 변경은 임시 공연 1개로 추가 확인했다. 모든 임시 공연 11개와 계정 2개는 확인 후 삭제했고, 실제 공개 공연 1개가 남은 미리보기를 제공한다. 실결제·환불·메시지 발송은 실행하지 않았다. 자동 통합 테스트는 별도의 Testcontainers PostgreSQL에서 실행한다.

최종 검증 결과, 비교 캡처, 의도된 차이는 [design-qa.md](../../design-qa.md)에 정리한다. 운영 반영 시에는 기존 배포 workflow/runbook으로 migration을 먼저 적용하고 API와 웹을 함께 배포한 뒤 live smoke를 수행해야 한다. 이번 작업의 로컬 검증을 운영 전환 완료로 해석하지 않는다.
