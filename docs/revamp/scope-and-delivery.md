# Grabit 전면 개편 범위와 완료 기준

결정일 2026-09-21. 사용자는 우리 팀이 운영하는 공연·팬미팅을 대상으로 기존 기록을 보존하는 전면 개편을 선택했고, 이후 추천안 선택과 후속 작업을 에이전트에게 위임했다. 아래는 그 권한으로 선택한 설계 기준이다. 사용자 인터뷰나 현장 검증을 대신했다고 주장하지 않는다.

## 제품의 완료 모습

구매자는 원하는 공연을 찾고 자신의 언어로 좌석·최종 청구금액을 확인한 뒤, 외부 결제창에서 돌아와도 같은 예매를 이어간다. 결제 여부를 모르는 동안 새 결제를 유도하지 않는다. 구매한 좌석마다 티켓과 특전을 확인하고, 취소 가능한 좌석과 환불액을 확인한 후 상태를 추적할 수 있다.

운영자는 공연을 선택한 뒤 준비·판매·거래·고객 대응·현장·정산을 같은 맥락에서 처리한다. UUID나 내부 상태 코드를 외워 입력하지 않는다. 조회 전·조회 실패·실제 0건을 구분하며, 금액을 바꾸거나 권리를 소비하는 조치는 대상·영향·사유가 명확하다.

현장 직원은 선택한 공연·회차와 좌석을 확인하고 입장 또는 특전 지급을 명시적으로 처리한다. 계정 하나의 다른 동행자가 자동 입장 처리되지 않는다. 통신이 끊겼을 때 대기 기록을 입장 확정이나 특전 지급 완료로 표시하지 않는다.

외부 주최자 입점, 타사 공연 판매 중개, 티켓 전매·가격 재판매 시장은 이번 범위에 추가하지 않는다. 고객의 기존 구매 기록·권리·정산 증거를 삭제해 설계를 단순화하지 않는다.

## 변경과 데이터 보존

- 기존 회원·Social Login Link·Reservation·Payment·Ticket Item·QR·동의·취소·입장·특전 이력 식별자를 보존한다.
- 원 결제액을 잔여 좌석 금액으로 덮어쓰지 않는다. 새로운 정책은 기존 구매 시점의 계약을 소급 악화시키지 않는다.
- PostgreSQL, NestJS modular monolith, Next.js, pg-boss, Valkey/Socket.IO를 출발점으로 유지한다. 프레임워크 교체나 별도 마이크로서비스는 이 문제의 해결에 필요하지 않다.
- URL 호환을 보존하고 내부 모듈·화면을 단계별로 교체한다. 출시 후보에서는 세 역할의 전체 흐름이 함께 통과해야 하며, 일부 화면 변경을 전면 개편 완료로 세지 않는다.
- 현장 기본 입장 단위는 기존 운영의 계정·회차 일괄에서 Ticket Item으로 바꾼다. 기존 입장 결과는 되돌리지 않고 새 스캔부터 명시적 좌석 단위 계약을 적용한다. 별도 ADR과 회귀 검증이 필요하다.

## 검증의 기준

| 검증층 | 완료 조건 |
| --- | --- |
| 단위·계약 | 실제 경계에서 상태·금액·반환 경로·허용 행동을 검증. 구현 구조를 복제한 테스트는 만들지 않음 |
| 격리 통합 | 실제 PostgreSQL/Valkey에서 좌석 경쟁·확정·발권·부분취소·입장·특전·재오픈 원자성과 멱등성 검증 |
| 브라우저 | 실제 API를 사용하는 구매자·운영자·현장 역할로 정상/실패/빈 상태/권한 제한 직접 조작 |
| 외부 연동 | 국내/해외 카드·Alipay·PayPal, SMS·메일·OAuth를 각각 실제 공급자 test 환경으로 구분해 증거 확보 |
| 실기기·현장 | iOS Safari/Android Chrome 앱 복귀, 카메라·통신 단절·실물 지급은 실제 환경에서 별도 확인 |
| 전환 | 보존 데이터 리허설·권리/금액 대조·중단/복귀 절차와 검증된 배포 revision 확인 |

현재 남은 외부/실기기 검증은 기존 고객 여정 검증 작업에 OPEN으로 유지한다. 원인을 모르는 Alipay 오류를 코드 결함이라고 단정하거나, 위젯이 보인다는 이유로 결제 성공을 선언하지 않는다. 이 미완료 상태는 구현/출시 검증표에 그대로 연결한다.

## 실행 순서와 목표 일정

12월 이전 전면 개편이라는 목표를 위한 작업 순서다. 날짜는 작업 목표이며 공급자·실기기·부하 결과를 확인한 완료 예측이 아니다. 다음 단계로 넘어가는 조건은 해당 증거의 통과다.

| 목표 구간 | 결과물 | 넘어가는 조건 |
| --- | --- | --- |
| 9월 21–27일 | 업무 결정·전체 UX 방향·명세·의존성 있는 구현 과제, 테스트 환경 분리 계획 | 범위/권리/금액/복구 책임과 미확인 gate가 모두 명시 |
| 9월 28일–10월 11일 | 구매자 탐색·인증·예매·결제·티켓·취소의 전체 흐름 | 핵심 거래 통합 회귀와 실제 test 결제/취소 |
| 10월 12–25일 | 공연 준비·판매·CS·현장·특전·정산 전체 운영 흐름 | 역할별 브라우저 시나리오 및 API 권한·원장 대조 |
| 10월 26일–11월 8일 | 통합 안정화·다국어·접근성·전환 리허설 | 37개 기존 route 대응과 전체 회귀, 데이터 불변식 |
| 11월 9–22일 | 실기기·PG·부하·장애·현장 실물 리허설과 수정 | 미실행/미확정 gate 해소 및 복귀 절차 실제 확인 |
| 11월 23–30일 | 출시 후보 고정·운영 인수·전환 | 명세 전체 완료와 안전한 오픈 검증 |

현재 자율 작업은 이 순서를 따라 연속 진행한다. 구현 가능한 부분을 미래 날짜까지 기다리는 일정은 아니다. 사람·장비·외부 서비스가 필요한 항목은 구체적인 준비 상태와 막힌 마지막 단계만 보고한다.
