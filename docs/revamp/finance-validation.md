# 정산 원장 검증 (#221)

2026-09-22. 격리 PostgreSQL/Valkey와 일반 브라우저의 재무 계정으로 확인했다. 원본 고객 데이터·운영 환경에 쓰지 않았고 실제 은행 입금이나 회계 마감을 확정하지 않았다.

## 변경과 실패 재현

기존 화면은 조회 전 0원, API에 전달하지 않는 필터, 취소 거래가 빠진 PG 대조, 근거 없이 입력한 외화 지급액과의 차이 계산을 제공했다. 새 `/ledger` 경계에서 원 주문/저장 결제액·확정/처리 중 환불·유효 티켓·유지 수수료·통화별 원본 PG 금액을 분리한다. 기존 화면 URL은 유지하며 구 재무 API는 명시적 410 전환 안내로 폐기했다(ADR 0012). DB migration은 없다.

- 실제 HTTP/DB에서 새 조회/내보내기 부재를 RED로 확인하고 구현했다.
- 기존 좌석 취소 후 나머지 예매 환불의 USD 영수증 누락, 전체 환불 거절·복구 후 과거 요청액 0원, 이전 시도 누락을 각각 재현하고 수정했다.
- 외화 snapshot 누락 시 KRW로 잘못 추론하던 경로, 잘못된 PG 날짜를 정상 0건으로 처리하던 경로, 티켓 발급 전 보상취소를 미환불로 표현하던 경로를 수정했다.
- 과거 좌석 취소 prepare 보상이 command를 지운 구간은 상태/금액을 미확인으로 처리하고 취소일 조회에서 대조 후보 경고를 유지한다. 보수적 판정의 한계는 runbook에 명시했다.
- 브라우저 연결 단절 중 React Query가 조회를 일시 정지했는데 캐시 금액이 계속 보이는 문제를 실제 조작으로 발견했다. 이제 연결 대기와 재조회를 표시하며 금액·CSV를 숨긴다.

## 자동 검증

- PostgreSQL/Nest HTTP finance 회귀 22/22 통과: KST 날짜 경계, 승인/취소일, asOf, 부분+전체 환불, 이전 요청 견적, 거절/복구, 원금 차이, KRW/USD, 미확인 전파, PG signed rows·잘못된 응답·0건·조회 실패, 권한, 내보내기 감사/개인정보, 구 계약 410.
- 기존 취소·발권 통합과 함께 83/83 통과 후 과거 증거 누락 회귀를 추가해 finance 22/22 재검증.
- API 전체 1,259/1,259, Web 전체 765/765, shared 148/148 통과 후 offline 회귀를 추가해 관련 UI 11/11 통과.
- shared/API/Web typecheck, API SWC build 통과. 변경 API/Web lint 오류 0건. API test 파일은 기존 eslint 설정상 대상 밖이며 integration/typecheck로 검증했다.
- Standards 최종 0건, Spec 최종 0건: 고정 `1f594dd05a3b15f20237ee1518267b933b089a7f`. 최초 지적을 RED로 재현해 해결했다. 레거시 2석 매출 관련 최초 지적 1건은 rowKey 오독으로 검토자가 철회했고, 처리 중 환불 집계의 실제 모순은 제거했다.
- Web production build 통과(`finance-web-production-build`). PR CI는 최종 commit 기준으로 후속 기록에 연결한다.

## 실제 브라우저·CSV

재무 capability 계정의 메뉴와 API 권한을 확인하고 테스트 전용 공연에 USD 부분 취소, KRW 처리 중, KRW 전액 취소 3개 주문/6개 Ticket Item을 준비했다. 이는 실제 공급자 거래가 없는 합성 표본이다.

1. 공연·회차와 KST 기간/기준 시각을 직접 선택: 원 주문/확정 결제 312,000원, 환불 누계 145,000원, 처리 중 45,000원, 유효 티켓 104,000원, 취소 수수료 5,000원, 유지 서비스 수수료 6,000원.
2. USD 별도 청구 8,000 / 확정 취소 3,461 / 잔액 4,539 minor units. KRW 청구 208,000 / 확정 취소 100,000 / 처리 중 45,000 / 계산 잔액 108,000을 별도 표시.
3. 취소일 9월 3일로 바꾸면 기간 내 승인 0원 / 환불 145,000원. 변경 직후에는 이전 금액을 숨기고 재조회한다.
4. 실 Toss test 정산 읽기는 해당 합성 키의 매칭 자료 0건을 반환했다. 이는 실제 상점 지급 검증이 아니다. PG 조회 시각과 미조회/성공 0건을 구분한다.
5. 브라우저에서 결제 원장 CSV와 좌석 CSV를 실제 다운로드했다. Python CSV 독립 검산으로 결제 3행의 총액/통화/기준 시각, 좌석 6행의 취소 3/처리 중 1/유효 2를 확인했다. 좌석 행에 원 주문액을 반복하지 않았고 이름/연락처/결제 키가 없었다. 성공 export 감사 기록 2건을 다시 조회했다.
6. 390×844와 데스크톱에서 필터·금액·통화·좌석 상세·내보내기·은행/마감 미확인 안내를 직접 확인했다. 모바일 clientWidth/scrollWidth 모두 390. 일시 viewport/오프라인 설정은 복원했다.

증거: private artifact `browser/66`–`76` 화면/상태/실제 CSV, `finance-state-final.json`, `tests/finance-*`. raw QR/인증/키는 보고서에 포함하지 않는다. IAB의 date input Playwright fill은 React 상태에 반영되지 않아 native `setValue`로 변경하고 적용된 조회 범위를 다시 확인했다.

## 남은 외부 경계

실제 상점의 국내/해외 정산 원본, 은행 실입금, 카드사 환불 반영일, 담당자 마감 승인과 실기기/현장 준비는 #214/#223에서 별도 증거가 필요하다. API/Web은 함께 배포·복귀하고 구 정산 화면을 새로고침한다. 과거 증거가 부족한 행의 미확인을 원금 수정이나 임의 0원 채움으로 해소하지 않는다.
