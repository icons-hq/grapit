# 구현 구조와 전환·검증 기준

2026-09-21 자율 위임으로 선택한 구현 기준. 기존 modular monolith와 실제 거래 데이터를 유지한다. 업무/거래/계정/현장 계약 및 UX 선택 기록과 함께 읽는다.

## 모듈과 인터페이스

- Next.js는 구매자·운영·현장 화면과 지역화된 탐색을 담당한다. 결제/좌석/환불/입장 상태를 브라우저가 추측해 확정하지 않는다.
- Reservation은 구매자의 주문 의도, canonical seat snapshot, 정책·deadline과 동일 주문 복구를 소유한다. Payment가 없는 준비 주문도 소유자에게 조회 가능하게 한다.
- Payment는 공급자 선택·키 scope·청구 quote·승인/취소 조회/멱등/진단을 소유한다. 공급자 HTTP 계약과 내부 원화 원장은 이 경계에서 변환한다. 프런트가 외화 청구액을 재계산하지 않는다.
- Ticket Item/QR/Admission/Benefit Redemption의 데이터 경계를 유지한다. 입장 소비는 한 Ticket Item에 제한하며 취소·발권·재오픈과 소유권/transaction 경계를 함께 검증한다.
- Admin 운영 화면은 기존 API capability와 감사 계약 위에 공연·회차 맥락 및 단계별 작업을 구성한다. 모든 페이지의 분산 fetch를 거대한 단일 client store로 옮기지 않는다.
- PostgreSQL은 원장, Valkey는 잠금·대기열·캐시·throttle·pub/sub, pg-boss는 지속 작업을 맡는다. Socket.IO 다중 인스턴스 broadcast를 유지한다. PG 네트워크 요청을 긴 DB transaction 안으로 옮기지 않는다.

큰 화면을 통째로 다시 쓰기보다 업무 단위로 작은 연결 요소를 추출해 페이지를 교체한다. 새로운 마이크로서비스/메시지 브로커/프레임워크 교체는 현재 발견된 문제의 필수 해결책이 아니므로 선택하지 않는다. 데이터·인증·PG 계약을 유지한 채 화면만 바꾸는 대안도 결제 복귀·입장 단위·환불 상태 문제를 해결하지 못하므로 선택하지 않는다.

## 보존과 전환

1. 기존 식별자, 회원/연결 계정, 원결제액, 구매 정책 snapshot, Ticket Item/QR 자격, 취소/입장/특전 이력과 원본 감사 자료를 보존한다.
2. 호환 API와 URL을 유지하면서 내부 구현과 호출부를 함께 검증한다. schema 변경이 필요한 경우 expand → backfill/대조 → 읽기 전환 → 나중 contract 순서를 따른다. 이번 기준만으로 운영 migration을 실행하지 않는다.
3. 결제/현장 계약은 하나의 통합 배포 단위로 검증한다. 오래된 클라이언트의 잘못된 동작을 막는 API 검증을 먼저 유지/추가한다. 입장 단위 변경은 ADR로 남기고 과거 입장 기록은 되돌리지 않는다.
4. 배포 전 원장 대조/rollback 자료와 이전 revision을 확보한다. 운영 판매를 열거나 닫는 일은 기술 배포와 구분한다. 외부 PG/실기기/현장/용량 gate가 남으면 '오픈 가능'으로 표시하지 않는다.
5. rollback은 이전 app revision으로 복귀하는 범위에서 수행한다. 새 승인·취소·입장·지급 사실을 DB 복원으로 지우지 않는다. 데이터 상태가 바뀐 뒤에는 그 사실을 보존하는 전진 수정 또는 호환 revision이 필요하다.

## 검증과 인수

| 단계 | 환경·담당 | 합격 증거 |
| --- | --- | --- |
| 거래 계약 회귀 | 에이전트, 격리 PostgreSQL/Valkey 및 공급자 대역 | 같은 주문 복귀, 좌석 단일 소유권, 중복 승인/취소, 마지막 좌석 수수료, 외화 상한/반올림, PG/DB 복구 |
| UI 회귀 | 에이전트, 실제 로컬 API + 브라우저 | 기존 37 route 연결, 구매자/운영/현장 persona, desktop/mobile, ko/en/th/zh-CN, 정상/빈/오류/권한 |
| 공급자 sandbox | 에이전트가 준비·조작, 본인 인증은 사용자 직접 | 국내/해외 카드·Alipay·PayPal 승인/복귀/취소, 실제 webhook 200·중복, OAuth/SMS/메일 전달 |
| 실기기·실물 | 실제 iOS/Android 및 현장 책임자 필요 | 앱 복귀·카메라·통신 단절/재연결·2대 동시 스캔·특전 재고/인수 |
| 부하/장애 | 격리 환경, 에이전트 | 단계적 100/500/1,000 동시 세션 실험, 좌석 경쟁·중복 결제 0, 서버 입장 중복 소비 0, 오류율/지연/자원 관측 |
| 데이터·정산 | 보존 snapshot, 원장/공급자/은행 자료 | 레코드·유효 권리·금액 총계와 표본 대조, 증빙 없는 실입금은 미확정 |
| 배포·전환 | 승인된 CI/CD, 에이전트 및 운영 책임자 | PR/CI/배포 revision·인증 smoke·오픈 flag/용량·rollback 확인 |

초기 성능 실험의 목표는 좌석 잠금 API p95 1초 이내, 구매 흐름 일반 API p95 2초 이내, 온라인 입장 처리 p95 1초 이내다. 이는 확정된 예상 고객 수나 인프라 보장치가 아니다. 실제 공연 판매 목표 인원/동시 트래픽은 아직 검증되지 않았고 부하 실험 결과로 용량을 산정한다. local 결과를 production 용량 증거로 사용하지 않는다.

실제 사람·기기가 필요한 단계는 담당 역할과 입력을 미리 준비한다. 에이전트가 물리 기기·본인 인증·실물 재고를 실행한 것으로 기록하지 않는다. 소액 live 결제/환불은 금액·대상과 인증이 구체화된 마지막 실행 단계에서 별도 기록한다.

## 구현 순서와 출시 판정

거래 복구·금액·환불 기반 → 구매자 전체 흐름 → 공연 준비·CS → 좌석별 입장·특전 → 정산/통합 → 외부·실기기·전환 리허설 순서다. 서로 독립된 화면 작업은 병행 가능하지만 안전 계약 변경은 통합 검증을 건너뛰지 않는다. 일정 목표는 범위 문서의 9–11월 구간을 유지한다.

완료는 명세의 모든 인수 기준과 검증표에 증거가 있는 상태다. '코드 작성 완료', '테스트 대역 통과', '배포 성공', '실제 오픈 준비 완료'를 각각 기록한다. 필수 gate가 미실행이면 해당 단계는 OPEN이며 일부 완료를 전체 개편 완료로 보고하지 않는다.
