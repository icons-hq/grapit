# Grabit 구매·운영·현장 전면 개편 명세

## Problem Statement

구매자는 가입 뒤 예매 경로를 잃고, 결제창에서 돌아오면 선택 좌석이나 예매를 다시 만들어야 하며, 실제 외화 청구액·환불 완료·남은 티켓을 화면에서 정확히 파악하기 어렵다. 운영자는 서로 떨어진 메뉴와 내부 식별자로 공연·거래·현장·정산을 연결해야 한다. 한 좌석 QR로 동행자 전체가 입장 처리되는 현행 정책은 따로 도착한 관객의 권리와 현장 집계를 혼동시킨다.

우리 팀의 공연과 팬미팅 운영 전체를 12월 오픈 이전에 개편한다. 기존 고객·구매 이력·유효 권리를 보존하고, 검증하지 않은 결제수단·실물·입금을 완료로 표시하지 않는다.

## Solution

고객은 자신의 언어로 공연을 찾고 인증·좌석·청구 금액을 확인해 예매한다. 외부 결제 복귀 후 같은 서버 주문을 확인하며, 좌석별 티켓과 취소 상태를 이어서 이용한다. 운영자는 공연·회차를 선택해 준비·판매·CS·현장·정산 업무를 수행한다. 현장은 한 좌석씩 입장과 특전 지급을 명시적으로 처리한다. 모든 역할에서 정상/대기/실패/권한 부족과 다음 행동을 일관되게 보여준다.

## User Stories

1. 첫 방문 구매자로서 공연명·일시·장소·가격·판매 상태를 먼저 보고 관람할 공연을 고르고 싶다.
2. 구매자로서 공연명·아티스트 검색과 상태/장르별 탐색으로 원하는 공연을 찾고 싶다.
3. 구매자로서 검색 결과 없음·종료·판매 예정 상태에서도 다음 탐색 행동을 알고 싶다.
4. 해외 구매자로서 ko/en/th/zh-CN 중 고른 언어가 가입·결제·티켓·지원까지 유지되길 원한다.
5. 구매자로서 공연장 기준 시간대와 실제 공연 시각을 보고 잘못된 날짜에 도착하지 않길 원한다.
6. 비로그인 구매자로서 가입/로그인/인증을 마친 뒤 선택한 공연의 예매로 돌아가고 싶다.
7. 구매자로서 인증 오류·재전송·만료에서도 입력과 다음 행동을 잃지 않길 원한다.
8. 기존 회원으로서 계정·소셜 연결·동의·설정 변경 후 기존 티켓의 소유권과 접근을 유지하고 싶다.
9. 구매자로서 마케팅 동의를 하지 않아도 기존 필수 자격을 충족하면 예매하고 싶다.
10. 구매자로서 대기열·좌석 잠금·결제 마감의 차이와 남은 시간을 이해하고 싶다.
11. 구매자로서 층·등급·가격과 선택 좌석을 함께 보며 모바일에서도 좌석을 고르고 싶다.
12. 구매자로서 다른 사람이 잡은 좌석이나 만료된 잠금에서 안전하게 다시 선택하고 싶다.
13. 구매자로서 티켓 가격·서비스 수수료·KRW 주문 합계와 실제 PG 청구 통화/금액을 결제 전에 보고 싶다.
14. 해외 구매자로서 실제 계정 국가에 맞는 결제수단과 안내를 받고 싶다.
15. 구매자로서 필수 약관과 해외 결제 안내를 직접 확인한 뒤 결제하고 싶다.
16. 구매자로서 결제창 중단·앱 복귀·새로고침 뒤 같은 서버 예매를 이어가고 싶다.
17. 구매자로서 승인 여부가 불명확할 때 중복 결제 없이 상태를 확인하고 싶다.
18. 구매자로서 늦게 승인되거나 콜백이 누락돼도 예매 확정 또는 명확한 복구 안내를 받고 싶다.
19. 구매자로서 예매 완료 뒤 각 좌석의 QR·입장·특전을 한곳에서 보고 싶다.
20. 구매자로서 일부 동행자가 입장한 뒤에도 남은 사람과 이미 입장한 사람의 티켓을 구분해 확인하고 싶다.
21. 구매자로서 취소 가능한 좌석과 수수료·환불액·남을 티켓을 확인한 뒤 일부 또는 전체를 취소하고 싶다.
22. 구매자로서 취소 요청·PG 처리 중·PG 완료와 카드사 반영을 구분하고 싶다.
23. 구매자로서 취소하지 않은 좌석의 QR과 특전이 유지되길 원한다.
24. 구매자로서 사용할 수 있는 티켓만 재발송하고 실패하면 이유와 재시도 방법을 알고 싶다.
25. 운영자로서 공연을 단계별로 준비하고 초안을 저장·재개하고 싶다.
26. 운영자로서 회차·좌석·등급·가격·언어·특전의 미완료 항목을 검수하고 해당 입력을 바로 수정하고 싶다.
27. 운영자로서 게시와 판매 개시를 구분하고 대상·일정·영향을 확인한 뒤 공개하고 싶다.
28. 운영자로서 판매 중 변경이 기존 구매자의 가격·정책·좌석 권리를 바꾸지 않길 원한다.
29. 운영자로서 공연·회차를 선택해 좌석 운영·예매·현장·정산으로 이동하고 싶다.
30. 운영자로서 UUID를 외우지 않고 제목·날짜·좌석으로 업무 대상을 고르고 싶다.
31. CS 담당자로서 문제 거래를 찾고 원 주문·PG·좌석·QR·입장·취소·전달 이력을 함께 보고 싶다.
32. CS 담당자로서 공급자 조회 실패를 미확정으로 유지하고 중복 결제/취소 없이 대조·복구하고 싶다.
33. 운영자로서 특전 identity를 실수로 바꾸지 않고 제공 조건·배정·결과 고정을 관리하고 싶다.
34. 운영자로서 테스트 배정과 실제 고객 권리를 구분하고 이미 지급된 결과를 보존하고 싶다.
35. 현장 직원으로서 회차와 좌석이 일치하는 티켓 한 장만 입장 처리하고 싶다.
36. 현장 직원으로서 중복/동시 스캔을 구분하고 인원을 중복 집계하지 않길 원한다.
37. 현장 직원으로서 입장과 별도로 품목별 특전을 지급하고 중복 수령을 막고 싶다.
38. 현장 직원으로서 카메라 실패에 대체 입력을 사용하고 취소·다른 회차 티켓은 거부하고 싶다.
39. 현장 직원으로서 통신 단절 중 기록을 대기로 보고 재연결 때 충돌을 확인하고 싶다.
40. 현장 직원으로서 서버 미확정 기록과 실제 특전 지급을 혼동하지 않길 원한다.
41. 재무 담당자로서 원 주문·취소·서비스/취소 수수료·PG 청구/취소/정산·은행 실입금을 구분하고 싶다.
42. 재무 담당자로서 통화와 기준 일자가 명시된 화면·CSV를 원장과 재계산하고 싶다.
43. 재무 담당자로서 미조회·조회 실패·실제 0건과 증빙 미확인을 구분하고 싶다.
44. 관리자로서 운영/검수/승인/재무/현장 권한을 나누고 API에서도 같은 제한을 보장하고 싶다.
45. 관리자로서 중요한 변경의 대상·사유·전후 상태·담당 이력을 추적하고 싶다.
46. 운영 책임자로서 기존 회원·거래·권리를 보존하는 전환과 거래 사실을 지우지 않는 rollback 절차를 원한다.
47. 운영 책임자로서 실제 테스트한 환경과 아직 미실행인 PG·실기기·실물·용량 항목을 보고 오픈 여부를 판단하고 싶다.
48. 모든 사용자로서 작은 화면·키보드·확대·장문에서도 주요 정보와 조작에 접근하고 싶다.

## Implementation Decisions

- 기존 Next.js/NestJS modular monolith, PostgreSQL, Valkey/Socket.IO, pg-boss를 유지한다. 주문·권리·공급자 거래의 경계를 보존하며 역할별 페이지를 교체한다.
- 준비 Reservation은 Payment 유무와 관계없이 소유자에게 조회 가능하다. 외부 결제 전 고정 orderId를 복귀 경로에 보존한다. 새로고침과 빈 client store에서도 canonical 서버 snapshot을 복구한다.
- 승인 불명/실패 query는 재결제·취소의 근거가 아니다. 서버 확인 후 확정/재개/만료/확인 중으로 나눈다. 정상·중복 webhook은 HTTP 200을 반환한다.
- 청구 quote는 서버 소유다. 주문 KRW와 PG 통화/금액, 환불 통화/금액을 함께 표시한다. locale를 국가로 대체하지 않는다.
- 좌석별 부분취소는 기존 정책·공급자 가능 여부·권리 사용·멱등/동시성 검증 뒤 제공한다. 마지막 좌석의 수수료, 외화 minor-unit 잔액과 누적 상한을 보존한다. 환불 상태는 inventory reopen 상태에서 계산하지 않는다.
- 새 입장은 한 Ticket Item만 소비한다. 이미 입장한 Ticket Item의 QR 조회를 유지한다. 특전 지급은 별도 기록이며 offline 확정 지급은 제공하지 않는다.
- 화면은 공연·회차 맥락, 단계별 준비, 운영 인박스와 예매 상세, 명시적 현장 행동을 중심으로 구성한다. 실제 API 권한과 감사 기록을 유지한다.
- 시각 방향은 Image Gen 참고와 직접 조작한 별도 시안에서 선택했다. 가상 공연·수치·저장 카드 UI·시안의 공급자 대역은 제품에 포함하지 않는다. 사용자의 자율 위임에 따른 에이전트 결정이며 사용자 피드백으로 가장하지 않는다.
- 원 회원·주문·결제 금액·정책·권리·입장/지급 이력을 보존한다. 필요한 schema 변경은 expand–contract 방식으로 검증하고 기존 URL을 호환한다.

## Testing Decisions

- 내부 함수 호출 횟수보다 사용자에게 보이는 계약과 실제 상태 변화/거부를 검증한다. 기존 서비스/HTTP controller, PostgreSQL/Valkey 통합, 실제 페이지·PG sandbox 순으로 증거를 확보한다.
- 결제 복귀는 페이지를 remount해 같은 주문 복구를 확인한다. 메모리가 남은 단순 rerender만으로 통과시키지 않는다.
- 취소·입장·특전은 실제 원장과 QR·inventory·잔액을 함께 검증한다. 동일/역순 webhook·동시 요청·PG 성공/DB 실패·재시도를 포함한다.
- 기존 일반 회귀와 재오픈 통합 사례를 보존하고 UI 언어·금액·실패 상태의 계약 테스트를 추가한다. webhook은 실제 HTTP 응답 코드로 검사한다.
- 각 역할의 실제 브라우저 조작과 desktop/mobile 시각 검수, 4개 언어의 경로/문구, 37개 기존 route 대응을 확인한다.
- 실제 공급자/실기기/실물/은행 증빙/production 부하는 대역이나 local 결과로 대체하지 않는다. 미실행은 출시 gate에 OPEN으로 남긴다.

## Out of Scope

외부 주최자 셀프 입점 marketplace, 타사 공연 판매, 티켓 전매 시장, 새 SNS 커머스, 이유 없는 스택/서비스 분리, 기존 고객 권리 삭제는 포함하지 않는다. 확정되지 않은 법적 수수료·보존기간을 새 정책으로 임의 도입하지 않는다.

## Further Notes

현행 진단, 일반 고객 실제 sandbox 결제·취소, 가맹점 설정 확인과 설계 결정은 [Grabit 전면 개편 의사결정 지도](https://github.com/icons-hq/grapit/issues/199)에 연결돼 있다. 국내 Hyundai와 해외 Visa sandbox 전체 승인/취소는 실행했고, Alipay·PayPal·실제 모바일·외부 인증/전달 등 남은 검증은 [설계 전에 일반 고객의 전체 예매·결제·취소 여정을 직접 검증한다](https://github.com/icons-hq/grapit/issues/214)에 계속 기록한다.

실행 목표는 9–11월 전면 개편·안정화·전환 준비이며 가능한 구현은 즉시 연속 진행한다. 기술 배포 완료와 실제 판매 오픈 준비 완료는 별도로 판정한다.
