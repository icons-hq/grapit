# 공연 준비·판매·고객 대응 검증

Issue #219. 사용자 자율 위임과 기존 구현·검증 계약에 따른 작업이다. 운영 DB와 고객 권리는 변경하지 않는다.

## 검증 경계

- 실제 Nest HTTP + 역할/capability guard + 서비스 + 일회용 PostgreSQL: 역할별 공연 변경, 공개 우회 차단, 초안 저장/재개/충돌, 공개 준비 판정과 감사 기록을 검증한다. 인증된 사용자 입력만 테스트 middleware로 공급하고 권한 guard는 실제 구현을 사용한다.
- 실제 서비스 공개 API: 판매 중 좌석/가격/회차 보호, 특전 identity 보존, CS 조회·조치 이력을 검증한다. 외부 PG·메일·캐시는 명시한 경계에서만 대역을 허용한다.
- 실제 브라우저: 격리 localhost API와 역할별 합성 계정으로 제목/날짜 선택, 단계별 편집, 저장/재개, 검수 오류 이동, 권한별 메뉴와 CS 연결을 직접 조작한다.
- 디자인: `concepts/admin-preparation-v1.png`의 공연 맥락·준비 체크리스트·작업 영역 계층을 구현 화면과 비교한다. 시안의 공연명/건수는 실제 조회 결과로 대체한다.

## 구현 계약

- `performance_drafts`는 작성자에게만 보이는 부분 입력이다. 초안 revision으로 중복 저장을 거부하고, 공연 기준 `updatedAt`이 바뀌면 반영을 거절한다. 초안·공연 반영·감사 영수증은 같은 PostgreSQL transaction에 있으며 중복 반영은 같은 공연을 반환한다.
- 신규 공연은 비공개로 생성한다. 일반 생성/수정 API로 공개 상태·승인자·승인 시각을 바꿀 수 없다. 공개 승인은 실제 회차·좌석·가격·결제수단·현재 원문과 일치하는 게시된 ko/en 콘텐츠를 검사한다. 확인한 공연 `expectedUpdatedAt`이 달라지면 다시 검수해야 한다.
- 기존 단독 좌석도 저장 API도 공연 버전을 갱신하고 감사 기록을 남긴다. 오래된 초안이 이 경로의 최신 좌석·정책을 덮을 수 없다. 수정 버전 시각은 밀리초 단위에서도 단조 증가한다.
- 판매 중이거나 예매·좌석 운영 이력이 있는 공연은 좌석·가격·기존 회차·공연장 구조를 보호한다. 같은 좌석도·가격을 포함한 안내 수정은 기존 ID를 보존한다. 판매 전 가격 변경은 판매 좌석 가격에도 반영하며, 좌석도 없이 등급명만 바꿔 기존 배정을 고아로 만들 수 없다.
- 공유 공연장의 안내를 생략했다고 기존 안내를 지우지 않는다. 다른 공연이 참조하는 공연장의 내용을 일괄 변경하지 않는다. 상세 API는 입장·교통 안내를 편집 화면에 되돌려준다.
- 원문 변경은 번역 초안을 무효화한다. 검수/게시 UPDATE는 읽었던 상태와 원문 hash를 다시 비교하여 진행 중 요청이 `stale`을 덮지 못한다. 공개 조회도 현재 공연 원문과 hash가 일치하는 검수본만 사용한다.
- 일반 고객의 좌석 잠금·예매 준비는 공연 공개를 요구한다. 기존 관리자 미리보기 우회는 유지하되 고객의 공개·판매 개시 조건과 구분한다.
- `reservations.read`를 예매 목록·상세·고객 대응 근거에 적용한다. 운영/검수/승인/재무는 조회하고 현장은 조회할 수 없다. 현장 bundle은 로그인·JWT 발급·프로필 새로 조회에서도 보존한다. 배너 전용 권한은 배너 업로드만 허용한다.
- 문의의 공연/회차 필터는 연결된 예매를 기준으로 적용한다. 답변 저장 중 중복 조작을 막고 실패한 입력은 남긴다. 공연을 바꾸면 이전 문의 선택·입력을 새 대상의 조치에 재사용하지 않는다.
- CS 근거 조회는 PG 호출·QR 발급·이메일 발송을 하지 않는다. 원 주문 KRW, 실제 PG 청구 통화/minor 금액, 확인 시각, 확정 취소 누계, 좌석/특전 권리와 발송 이력을 읽는다. 최신 PG 미조회, 카드사 반영 미확인, 수신함 도착 미확인을 별도로 표시한다.
- 특전 identity는 화면이 생성하고 기존 값을 보존한다. 외국어 copy, 테스트/실제 배정, 결과 고정 시각, 지급 시도 이력을 구분한다. 지급 시도가 시작된 결과의 구성·실제 배정 변경은 기존 결과 잠금 계약에 따라 거부한다.
- 공연·회차 선택은 URL로 이어지고 잘못된 소속 회차는 사용하지 않는다. 일반 예약 CSV는 선택 공연의 전체 회차 범위이며, 회차 구매자 명단은 선택 회차의 활성 티켓 범위임을 표시한다. 일반 CSV의 회차별 확장은 재무 업무 과제에서 다룬다.

## 실제 브라우저 검증

localhost Web 3000/API 8080, PostgreSQL `127.0.0.1:55432/grabit_journey`, Valkey 56379, 합성 계정만 사용했다. 신규 draft migration 전후 예매 12건·결제 6건·원금 합계 1,840,000원·Ticket Item 10건·QR 10건이 동일했다. 그 뒤 합성 공연·초안·번역·문의를 추가했다. 특전·현장 검증을 위해 해당 공연에 합성 주문 1건·결제 원장 104,000원 1건·Ticket Item 2건·QR 2건을 추가했다. 이 fixture는 외부 PG 거래와 이메일 발송을 하지 않았으며 기존 주문·결제·권리는 변경하지 않았다.

- 운영자: 제목만 입력한 초안 저장 → 목록 → 이어 쓰기 → 단계별 입력 → 2석 SVG 업로드/등급 배정 → KST 회차·판매 시작 → 한글 안내 → 검수 → 공연 반영. 입력 누락 시 해당 단계와 오류 메시지로 이동하며 공개를 자동 수행하지 않는다.
- 실제 조작에서 발견한 SVG object 차단, 다음 단계의 의도하지 않은 submit, 초 단위 datetime 변환, 새 회차의 빈 ID/유실되는 날짜, 빈 장소 안내의 가짜 dirty 상태를 수정하고 정상 등록/공개 경로를 재실행했다. SVG는 보안 헤더를 낮추지 않고 이미지 문맥에서 렌더링한다.
- 좌석 운영: 제목·KST 회차를 선택해 좌석 화면으로 이동 → A-1 판매 중지 → 사유·상태 이력 확인 → 판매 가능 상태 복원. 확인창에 공연명·회차와 좌석을 표시한다.
- 운영자는 영어 공연명/상세 안내를 검수하고 게시 버튼이 비활성인 것을 확인했다. 승인자는 같은 검수본을 게시하고 준비 상태가 바뀌는 것을 확인했다. 최신 공연의 회차·판매 상태·판매 시작·결제수단을 확인하여 공개한 뒤 구매자 페이지와 목록 반영을 확인했다. 테스트 환경의 번역문은 직접 작성한 합성 내용이다.
- 재무: 공연 준비 화면 접근 차단, 허용된 예매 조회에서 원 주문 104,000원, PG 원 청구/확정 취소 USD 70.72, 유효 0/취소 2석, PG 최신 미조회와 카드사 반영 미확인, 발송 기록 없음 확인.
- 현장: 최초 로그인에서 scanner bundle이 응답에서 빠지던 오류를 재현해 로그인/프로필 매핑을 수정했다. 새 로그인 후 예매 관리가 차단되고 허용된 현장 업무로 이동하는 안내만 제공되는 것을 확인했다.
- 고객 대응: 해외 카드 환불 문의에서 연결된 예매 근거를 열어 확인하고, 답변을 남긴 뒤 해결 상태로 변경했다. DB에서도 답변 1건과 해결 상태를 확인했다. 외부 메시지는 발송하지 않았다.
- 특전: 설정 없는 회차의 JSON 응답 오류를 실제 화면에서 재현·수정했다. ko/en/th/zh-CN 안내로 포함 특전·한정 특전을 저장 → 테스트 1회 → 실제 반영 1회 → 표시명 수정까지 조작했다. 테스트 뒤 권리 2건이 동일했고, 실제 반영 뒤 포함 2건/한정 1건이었다. 표시명 수정 후 3개 권리의 ID·티켓 연결·identity·상태·외국어 안내를 모두 대조해 보존을 확인했다.
- 모바일 390×844: 준비 체크리스트·공연/회차 선택·권한별 메뉴를 확인했다. 메뉴 이동 뒤 drawer가 남는 문제를 수정했다. DOM 폭/scroll 폭은 모두 390px였다. 화면 캡처와 DOM 판정을 함께 사용했다.

브라우저 증거는 저장소 밖 `grapit-revamp-autonomy-2026-09-21/browser/42-*` 이후, 테스트 결과는 같은 artifact의 `tests/operations-*`에 보관한다. 원본 QR·자격 증명·고객 식별자는 공개 문서/PR에 포함하지 않는다.

## 검토와 남은 검증

초기 고정 diff 검토는 Standards 0건, Spec 3건이었다. 단독 좌석도 충돌 누락, 오래된 공개 승인, 번역 무효화 경쟁을 실제 실패→수정→통과로 처리했다. 추가 Standards 검토에서 발견한 장소 null/빈 문자열의 가짜 변경도 실제 HTTP 실패→수정→통과로 처리했다. 최종 증분 재검토는 Standards 0건, Spec 0건이다. PR CI는 이어서 확인한다.

문의 연결·특전 브라우저 검증을 완료했다. 최종 Web production build도 통과했다. 현장 입장 정책/실기기와 정산 대조/은행 증빙, 전체 route·4개 언어 통합, 배포·판매 전환은 후속 과제의 완료 기준이며 이 문서의 테스트로 통과 처리하지 않는다.
