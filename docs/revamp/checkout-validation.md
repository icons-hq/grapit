# 결제 복구 개편 검증

구현 과제: [구매자가 같은 예매로 결제를 복구하고 실제 청구 금액을 확인한다](https://github.com/icons-hq/grapit/issues/216).
검증일: 2026-09-21. 격리된 로컬 PostgreSQL/Valkey, 일반 고객 계정, 실제 Toss **test** 가맹점 키를 사용했다. 실결제·운영 DB 변경은 실행하지 않았다.

## 완료한 흐름

- 최초 좌석 선택 → 해외 카드 최종 청구 금액 확인 → 전체 새로고침 → 동일 주문·좌석·마감·해외 카드·USD 금액 복구.
- 내 티켓의 미결제 주문 → 결제 계속하기 → 같은 준비 주문 복구.
- 결제 전 재선택 → 기존 준비 주문 종료 → 이전 좌석 해제 완료 → 새 좌석 선택 화면 이동.
- 공개 테스트 VISA → Toss sandbox 승인 → 사이트 복귀 → 확정 예매 및 좌석별 QR 1개 → 고객 취소.
- 내부 원 주문은 KRW 382,000, 서버와 Toss의 청구 금액은 USD 259.76으로 일치했다. 공급자 원거래 조회에서 승인 `DONE`, 이후 취소 `CANCELED`, 취소 항목 `DONE`, 잔액 0을 확인했다. 내부 Payment는 `CANCELED`, 활성 Ticket Item/QR은 0개, 폐기 QR은 1개다. 카드사 실입금 확인을 뜻하지 않는다.
- 자동완성 확장 프로그램 팝업은 직접 닫고 계속 진행했다. 일반 고객 화면의 실제 카드사 선택, 체크박스, 승인·취소 버튼을 조작했다.

## 자동 검증

- API unit 1,316개 통과. 공연별 예매 정책 조인이 추가되면서 기존 세 개 DB 대역의 조인 체인을 보완한 뒤 재실행했다.
- PostgreSQL 통합 27개 통과. 기존 좌석/결제/취소 회귀와 소유자 조회, Payment 없는 준비 주문, 고정 결제수단/외화 견적, 인계와 변경 경쟁, 불확실한 결제의 중도 종료 금지, 좌석 점유 검사 실패를 포함한다.
- Web unit 719개 통과. 문서 전체 remount, 빈 store, 소유 주문 복구 실패, 금액 검토 전 PG 호출 금지, 위젯 선택 경쟁, 좌석 해제 완료 전 재선택 금지를 포함한다.
- Shared unit 130개 통과. API/Web TypeScript 및 production build 통과. 변경 파일 lint 오류 0개; 기존 API 테스트의 경고와 통합 파일의 lint 대상 제외는 남아 있다.
- 정상/중복 webhook HTTP 200, 잘못된 요청 400, 처리 실패 500을 실제 Nest HTTP 경계에서 검증했다.

## 브라우저에서 추가로 발견한 문제

단위 테스트를 통과한 초기 구현은 `history.replaceState(window.history.state, ...)`가 Next.js의 내부 갱신으로 취급되어 라우터의 query 상태가 갱신되지 않았다. 후속 렌더에서 복구 주소가 사라지는 것을 실제 새로고침으로 재현했다. 외부 history 호출에 `null`을 전달해 Next.js가 내부 상태를 복사하고 query를 반영하게 고친 뒤, 신규 주문 주소 보존과 새로고침을 다시 확인했다.

## 교차 검토 후 보완

- 공급자 인계 뒤 Payment가 아직 없거나 `READY`인 주문을 재결제 가능한 주문으로 취급하던 경로를 수정했다. 결제창·완료 화면·예매 상세는 같은 판단 함수를 쓰며, `IN_PROGRESS`/`DONE`/`PARTIAL_CANCELED`와 인계 후 결과 미확인을 로컬 타이머보다 우선한다.
- 결제 조회 실패는 만료로 간주하지 않는다. 상태 재조회·내 티켓·고객센터를 제공하며, 승인 API의 좌석 충돌도 결과 조회를 거쳐 안내한다.
- 주문 주소는 prepare 요청 전에 저장한다. 서버가 커밋한 뒤 응답이 유실되는 테스트에서 같은 주문/좌석을 복구하고 추가 준비 주문이 생기지 않음을 확인했다.
- 로그인 가드는 같은 사이트의 주문 주소와 언어를 보존한다. 인증 대기·정상 로그인 복귀·탈퇴 분기를 검증했다.
- 인계 후 결과 미확인 주문은 기한이 지나도 결제 전 종료 API, 준비 API, 만료 worker가 임의 종료하지 않는다. 실제 PostgreSQL 실패 재현 후 수정했다. 서버 조회 미검색·오류만으로 결제 없음이라 판단하지 않는다.
- 두 탭이 같은 주문을 PG로 넘기는 경우 서버 CAS로 한 번만 허용한다. 순차 재요청과 동시 요청을 PostgreSQL에서 검증했다. 신규 prepare가 좌석 점유 조건으로 명확히 거절된 경우에만 아직 생성되지 않은 복구 주소를 제거해 재선택을 허용하며, 응답 유실은 계속 같은 주문을 조회한다.
- 실제 로그아웃 → `/en` 주문 주소 → 영문 로그인 → 같은 주문과 영문 종료 상태 → 영문 좌석 선택 복귀를 앱 내 브라우저에서 완료했다. Chrome에서도 로그인 후 동일 주문 주소 보존을 확인했다.
- 390px 영문 모바일 화면에서 공용 하단 메뉴가 결제 버튼을 가리는 결함을 발견했다. locale prefix를 제거한 실제 업무 경로로 전용 레이아웃을 판정해 고쳤으며 네 언어 회귀 10개와 모바일 재캡처로 검증했다. 수정 후 금액과 결제 버튼 모두 보이고 가로 넘침이 없다.
- 로컬 개발 서버는 접속 주소와 같은 `--hostname localhost`로 실행한다. `127.0.0.1`에 bind하고 `localhost`로 접근하면 Next rewrite가 외부 재요청으로 처리돼 언어 header가 초기화됐다. 서버 기동을 맞춘 뒤 `/en/auth`, `/th/auth`, `/auth`의 SSR 언어를 각각 확인했다. 이 환경 원인을 제품 번역 결함과 구분했다.
- 최신 영문 viewport 캡처는 앱 내 브라우저의 PG 위젯 로딩/실패 상태다. 이 도구에서 외부 위젯이 차단되는 한계가 있으며, 실제 공급자 위젯·승인·취소 결과는 별도의 Chrome 증거로 판단했다.

## 남은 과제와 전환 조건

- 취소 후 확인 모달이 남는 문제, 이미 PG 취소가 끝난 주문의 환불 상태, 취소 견적의 외화 금액, 취소된 주문의 메일 버튼은 다음 [좌석별 티켓·취소 과제](https://github.com/icons-hq/grapit/issues/218)에서 처리한다. 이번 실제 테스트에서도 모달 잔류를 재현했다.
- 실제 Alipay·PayPal 사용자 인증, 해외 SMS/메일/OAuth, 물리적 iOS/Android와 현장 단말은 [외부 검증 과제](https://github.com/icons-hq/grapit/issues/214)가 열려 있다. 데스크톱 viewport 검증으로 이를 대체하지 않는다.
- nullable migration은 로컬 DB에만 적용했다. 기존 예매 6개·결제 2개·결제 원금 KRW 1,146,000·Ticket Item/QR 각 3개가 적용 전후 동일함을 확인했다. 이후 브라우저 테스트로 생성된 주문은 이 보존 검사와 별도다.
- 전환 전, 기존 `checkout_payment_method`가 없는 미결제 주문을 종료·대조해야 한다. 기존 결제/회원/티켓 기록은 변경하지 않는다.

원 증거는 로컬 `.codex/artifacts/grapit-revamp-autonomy-2026-09-21/`의 `tests/`, `browser/`, `migration-evidence.json`, `checkout-payment-done.json`, `checkout-payment-cancelled.json`에 있다. 공개 문서에는 결제 키·고객 인증 정보·QR 원문을 포함하지 않는다.
