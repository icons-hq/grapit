# 공지 이후 가입 모니터링

관리자 → 회원 관리(`/admin/users`) 상단에서 확인한다. 기존 개별 회원 화면의 권한은 바꾸지 않는다. 집계 API `GET /api/v1/admin/users/signup-monitoring`은 admin 역할과 `audit.read`를 요구하며 PII 또는 회원 ID를 반환하지 않는다.

## 기간과 해석

- 기본값은 한국 시간 오늘 00:00. 공지 시각을 입력해 적용하거나 최근 24시간·7일을 고른다. 공지 시각은 해당 브라우저에 저장하며 다른 관리자·기기로 공유하지 않는다.
- 공지 시각은 현재 이전, 최근 90일 이내다. `[시작, 조회 시각)`을 집계하고 바로 앞의 동일 길이 구간과 비교한다. 이전 구간이 0명이면 증감률은 미산출로 표시한다.
- 열린 화면은 60초마다 갱신한다. 백그라운드에서는 중단한다. 오류 시 이전 수치를 최신 결과로 표시하지 않는다. 마지막 갱신 시각은 서버가 응답한 시각이다.
- 일반 회원만 포함한다. 탈퇴 계정은 포함하고 병합·관리자는 제외한다. 영구 삭제된 회원은 복원할 수 없으며 현재 역할·병합 상태가 달라지면 과거 집계도 달라질 수 있다.
- 인증·마케팅 동의는 가입 당시가 아닌 조회 시점 상태다. 국가·언어는 회원 프로필 기준이다.
- 가입 방식은 가입 직후 1분 이내 생성된 가장 이른 소셜 계정을 우선하고,연결이 없으면 비밀번호가 있는 계정을 이메일로 분류한다. 그 외는 확인 불가다. 현재 테이블만으로 최초 가입 방식을 완전히 복원할 수 없으므로 화면에서 **추정**으로 표시한다. 한 회원은 한 방식에만 포함한다.
- 가입 → 첫 결제 전환은 선택 구간 신규 회원 중 가입 후 조회 시각까지 결제 완료 예매가 한 건 이상 있는 회원이다. 기존 `payments.paid_at`과 `DONE`/`CANCELED`, `reservations.CONFIRMED`/`CANCELLED`를 읽는다. 이후 취소된 예매도 포함하며 발권되지 않은 `FAILED` 보상 취소와 미승인 결제는 제외한다. 예매 횟수에 관계없이 한 명으로 센다. 예매 상태만으로 승인 시각을 판단할 수 없어 기존 결제 테이블도 조회한다. 새 데이터 수집·결제 처리 변경은 없다.
- 공지의 인과 효과를 증명하는 지표는 아니다. 요일·시간·다른 홍보의 영향이 섞이며 유입 경로는 1단계에서 수집하지 않는다.

## 확인 주기

공지 후 30~60분에 가입·인증이 발생하는지, 당일 3~4시간 뒤와 마감 때 동일 구간 대비 증가와 인증 이탈을 확인한다. 이후 7일은 하루 한 번 가입과 첫 결제 전환을 함께 본다. 판매 전이라면 결제 전환 0은 정상일 수 있다. 일일 요약은 반복 확인 부담이 생길 때, 임계치 알림은 평소 시간대별 기준치가 생긴 뒤 도입한다. 알림·스케줄은 이 PR에서 생성하지 않는다.

## DB 비용과 인덱스

운영 DB에 직접 접속하지 않고 격리된 PostgreSQL 16에서 실제 migration을 적용한 뒤 합성 회원 100,000명(1분 간격)을 넣었다. 최근 6시간, `role = 'user' AND account_status <> 'merged'` 날짜 범위의 `EXPLAIN (ANALYZE, BUFFERS)` 결과:

| 조건 | 실행 계획 | 실행 시간 | shared hit blocks |
| --- | --- | ---: | ---: |
| created_at 인덱스 없음 | Seq Scan | 7.800 ms | 2,041 |
| created_at B-tree | Index Scan | 0.063 ms | 10 |

이 결과는 로컬 날짜 필터의 선택도 검증이며 운영 전체 집계의 응답 시간 보장은 아니다. `users.created_at` 인덱스를 추가한다. 집계는 한 SQL snapshot으로 읽으며 범위를 90일로 제한한다. 배포 시 migration은 승인된 CI/CD 절차를 따른다. 운영 적용·배포는 별도 승인 대상이다.
