2026-11-03 기준: **판매할 공연·판매 시작 시각은 미정**, **현장 리허설 담당자는 박상우**다. iPhone 국내 카드 구매·전액 취소를 검증했고 Android·실제 현장 리허설은 보류했다. 장애 대응은 박상우 1차·이세원 이사 대체로 정했으며 연락·인수는 사용자가 직접 처리한다. 아래는 실행 순서와 판정 기준이며, 빈 결과를 합격으로 취급하지 않는다.

## iPhone 구매 흐름

### 실제 기기 연결 방법

사용자 요청에 따라 이번 검증은 공식 npm의 Appium WebDriverAgent를 Xcode/XCTest로 서명 빌드·실행해 실제 iPhone을 제어한다. 최초 Apple 개발자 약관 갱신은 사용자가 직접 동의한 뒤 서명을 재시도했다. 연결 대상의 실제 모델/OS를 확인하고, 기기 UI 요소 탐색·클릭·입력과 화면 캡처로 증거를 남긴다. 개발 서버는 Mac loopback USB relay 또는 기존 Xcode CoreDevice 터널로 접근하며 공개 네트워크에 노출하지 않는다. USB relay에서 기기가 보이지 않지만 기존 CoreDevice 터널이 정상인 경우 그 터널의 WDA `/status`로 대상 OS를 재확인하고 연결한다. 작업 종료 시 소유한 테스트 프로세스를 정리하고 임시 자동 잠금 300초를 원래 120초로 복구한다.

대안으로 Safari 웹 검사에는 Mac 기본 `safaridriver`를 사용할 수 있다. 새 세션의 `platformName=iOS`, `safari:useSimulator=false`, `safari:deviceType=iPhone`, `safari:deviceUDID=<연결된 실제 기기>`를 함께 지정해 Mac Safari나 시뮬레이터 결과와 섞이지 않게 한다. 기기 식별자 원문·세션 식별자·로그인 값은 공개 증거에 넣지 않는다. 세션이 생성된 뒤 실제 OS/브라우저, 현재 URL, 화면과 동작 결과를 기록한다.

기기에서 설정 → 앱 → Safari → 고급의 **웹 속성(Web Inspector)**과 **원격 자동화**가 필요하다. 기존 값을 먼저 기록하고, 사용자가 승인한 항목만 켠 뒤 작업 종료 시 이번 작업에서 바꾼 값을 복구한다. 기기 잠금·Face ID·카드 인증은 소유자가 직접 완료한다. Mac의 개발자 도구 설치나 USB 페어링만으로 Safari 자동화가 가능한 것으로 판정하지 않는다.

iPhone 미러링은 설정·화면 조작 보조에 쓸 수 있지만 카메라와 Face ID를 제공하지 않는다. 실제 QR 촬영에는 휴대폰을 직접 들어 촬영하는 단계가 필요하다. 다른 기기에서 Appium/XCUITest를 사용하려면 해당 기기의 서명된 WebDriverAgent 설치·기기 UI 자동화 권한을 준비한다. 어느 방식도 실제 촬영, 두 단말 동시 처리, 실물 인수 결과를 대체하지 않는다.

근거: 설치된 Apple `safaridriver(1)` 설명서, [WebKit 원격 검사 설정](https://webkit.org/web-inspector/enabling-web-inspector/), [Apple iPhone 미러링 제한](https://support.apple.com/en-us/120421), [Appium 실제 기기 준비](https://appium.github.io/appium-xcuitest-driver/10.43/getting-started/device-setup/).

상세 동작과 통신 장애 예외는 [좌석별 현장 운영](seat-level-field-operations.md)을 따른다. 기기 1대와 PC 탭 조합은 준비 점검에는 쓸 수 있으나 실제 휴대폰 2대 리허설 합격으로 기록하지 않는다.

### Wi-Fi를 쓸 수 없는 현장

Wi-Fi 자체는 필수 조건이 아니다. 각 검표 단말의 LTE/5G로 서버에 연결할 수 있어야 한다. 현장 입구·대기열·특전 배부 위치에서 실제 관객이 모일 시간대의 통신 상태를 확인하고, 가능하면 다른 통신사 SIM/핫스팟을 예비 회선으로 준비한다. 이 문서의 권장은 회선 구매나 계약 승인 또는 실측 완료를 뜻하지 않는다.

완전한 통신 단절에서는 새 QR의 유효성·취소·중복 여부를 확인할 수 없다. 서버 확인을 이미 마친 티켓만 입장 요청 실패 시 기기의 동기화 대기로 저장할 수 있으며, 대기는 서버 확정 인원에 포함하지 않는다. 단절 중 검표 탭을 새로 고치거나 로그아웃하지 않는다. 신규 입장은 보류하거나 현장 책임자가 예매번호·좌석·시각·담당자를 예외 원장에 적어 판단하고, 연결 복구 후 서버에 대조한다. 특전은 성공 확인 전에 실물을 지급하지 않는다. 실제 2단말·현장 회선 리허설은 보류 상태다.

## 소액 live 결제·환불 실행 기록과 재실행 기준

2026-11-03 사용자 승인으로 **시험용 미래 회차의 1석, 티켓 1,000원 + 좌석별 예매 수수료 2,000원 = 총 3,000원 1건**을 승인·전액 취소하고 시험 공연을 판매 종료·비공개로 복구했다. 재실행은 새 대상·금액·소유자 승인을 별도로 고정한 뒤 진행한다. 외화 수단은 실제 결제 화면의 통화·청구액과 별도 한도를 먼저 고정한다.

1. 공연일 이전 날짜에 결제하고 같은 KST 날짜 안에 취소한다. 현 코드의 당일 취소 경로는 서비스 수수료를 포함하지만, 실제 실행 직전 취소 미리보기의 환불액을 다시 확인한다. 관람일 당일 취소는 허용되지 않는다.
2. 소유자가 카드/지갑 인증을 직접 완료한다. 주문별 PG 승인·내부 결제·확정 예매·Ticket Item·QR을 대조한다.
3. 구매자 취소 화면의 예상 환불액을 확인하고 전체 취소한다. PG `CANCELED`/잔액 0·내부 취소·QR 회수·보류 종료 후 좌석 재개방을 확인한다.
4. 카드사/지갑의 실제 취소 반영과 가맹점 정산 원본·은행 입금을 별도로 대조한다. PG 승인 취소만으로 은행 단계까지 완료 처리하지 않는다. 카드/계좌 번호 원문은 보고서에 넣지 않는다.
5. 입장 처리한 현장용 티켓과 live 환불용 티켓을 구분한다. 이 계획으로 실제 거래나 기존 고객 환불을 자동 실행하지 않는다.

당일 전액 취소가 매입 전에 끝나면 새 시험 주문의 가맹점 은행 입금 자체가 발생하지 않을 수 있다. 이 주문은 PG 취소·카드사 반영·정산 대상 제외/상계까지 확인하고, **가맹점의 실제 은행 입금 대조는 승인된 기존 지급 완료 건의 PG 정산 원본과 해당 입금 자료**로 별도 수행한다. 새 주문의 잔액 0이나 PG 조회 0건을 은행 대조 완료로 바꾸지 않는다. 새 거래의 정산 지급까지 검증하려면 다른 실행안·한도·정산 예정일·환불 시점을 먼저 확정한다. [토스 취소 정책](https://docs.tosspayments.com/guides/v2/cancel-payment), [원장·PG·은행 대조 절차](finance-ledger-reconciliation.md)를 따른다.

## 공연별 오픈 직전

1. 공개 상태, 판매 KST, 회차, 층·좌석 수, 가격·수수료, 1인 제한, 결제 수단, 한국어·영문 안내와 번역 상태를 운영 화면에서 검토한다.
2. 지정 판매·입장 시간을 Valkey maintenance 보호 구간에 넣어 [판매 posture 검사](../../scripts/managed-demo/verify-valkey-sale-posture.mjs)를 다시 실행한다. 현재 maintenance는 수요일 18:00 UTC(목요일 03:00 KST)이므로 실제 일정과 대조해야 한다.
3. 판매 최소 15분 전에 API 8대와 Web 12대를 예열한다. [현재 용량 절차](managed-demo-cost-floor.md#current-600-seat-opening-profile--2026-11-02)에 따라 실제 최소·Ready 상태·관측 인스턴스 수를 확인하고 `node scripts/managed-demo/warm-web-routes.mjs`로 홈·예매 상태 조회가 Web 12대 각각에서 성공한 것을 확인한다. API 예열 Scheduler의 정기 예약은 공연 일정이 확정되기 전 일시정지 상태를 유지한다. 0대 cold start는 정합성을 지켰지만 진입 p95 13.8초로 지연 목표에 미달했다. 예열 완료 전 판매를 시작하지 않는다.
4. 진행 중 결제·환불, 백업, worker 최근 성공, [운영 감시](launch-monitoring.md)의 활성·실제 수신·담당자 인수, 복구 대상 revision/worker 이미지를 확인한다. 판매 중 겹친 배포의 DB 연결 예산은 별도다.
5. 해당 공연의 Gate Ledger에 날짜·실행자·증거·남은 예외를 연결한다. 공연이 지정되지 않은 과거 ledger나 이 문서만으로 공개 오픈을 승인하지 않는다. #214/#223은 실제 미완료 조건이 사라질 때 닫는다.
