# 공연 확정 후 실운영 인수

2026-11-02 사용자 확인: **판매할 공연·판매 시작 시각은 미정**, **현장 리허설 담당자는 박상우**, 준비 가능한 테스트 기기 종류는 **아이폰**이다. 안드로이드 실기기 확인과 전체 장애 대응 당직 배정은 아직 완료되지 않았다. 아래는 실행 순서와 판정 기준이며, 빈 결과를 합격으로 취급하지 않는다.

## 실행 전에 고정할 값

| 항목 | 현재 값 / 채울 내용 |
| --- | --- |
| 공연 / 회차 / 판매 시작·종료 KST | 미정 |
| 예상 동시 방문 / 좌석 / 예매 입장 상한 | 운영에 DB 4 vCPU·15GiB / API 최대 8대·pool 8 / Web 최대 12대 / 입장 150명 적용 완료. 1,500명 방문·600석의 시험 범위와 비용은 [전환 기록](../research/booking-production-cutover-2026-11-02.md) 확인. 실제 공연 규모가 달라지면 다시 판단 |
| iPhone 모델 / iOS / Safari 버전 | 기기 확보 후 기입 |
| Android 모델 / OS / Chrome 버전 | 미확보. Android 합격 기록 없음 |
| 현장 리허설 책임자 | 박상우 |
| 검표 기기 수 / 현장 Wi-Fi / 예비 회선 | 기입. 다중 단말 판정에는 실제 기기 2대 이상 필요 |
| 운영 장애 대응 담당·연락 경로·대체 담당 | 미정 |

| 공개 오픈 판단 | 공연별 증거가 채워질 때 결정. 기술 배포와 구분 |

기존 Girl Rules 관객·예매·QR·특전은 시험 데이터로 사용하지 않는다. 리허설은 식별 가능한 시험 공연/회차·시험 주문으로 준비한다. URL에 QR 원문, OTP, 비밀번호, 결제 키를 기록하거나 공유하지 않는다.

## iPhone 구매 흐름

시험용 외부 결제 환경이 준비된 뒤 아래를 Safari에서 진행한다. 카카오/네이버 등 앱 내 브라우저를 판매 채널로 사용한다면 해당 앱 안에서도 4~6번을 반복한다. PC의 모바일 화면 크기 검사와 실제 앱 전환 결과는 따로 적는다.

결제별 실제 test 승인·취소·웹훅 증거는 [현재 릴리스 기록](../revamp/release-readiness.md)과 함께 확인한다. Alipay/PayPal의 PC sandbox 성공을 iPhone 지갑 앱 성공으로 바꾸어 적지 않는다.

## 현장 리허설 — 박상우

`/field/check-in`에 검표 권한 계정으로 로그인한다. 시험 회차에 유효한 2석 예매, 취소된 티켓, 다른 회차 티켓, 테스트 특전 품목을 별도로 준비한다. 표의 A/B는 서로 다른 좌석이다. 실제 품목·초기 수량은 [실물 인수 대장](benefit-physical-handoff.md)에 적는다.

| 순서 | 동작 | 전산·실물 합격 기준 | 실행 시각 / 결과 |
| --- | --- | --- | --- |
| 1 | 기기별 시험 회차 선택, A QR 카메라로 읽기 | 확인만으로 입장되지 않음. 회차·좌석·입장 가능 표시가 맞음 | 미실행 |
| 2 | A만 입장 처리 | A 입장 1건, B는 미입장. 구매자 화면의 두 QR 조회 유지 | 미실행 |
| 3 | A를 두 기기에서 다시 읽기 | 이미 처리된 상태·이전 시각 표시. 새 입장 성공 없음 | 미실행 |
| 4 | 미사용 B를 실제 기기 2대에서 거의 동시에 입장 처리 | 성공은 정확히 1건. 다른 요청은 중복으로 구분 | 미실행 |
| 5 | 유효 QR 확인 후 회선을 끊고 입장 요청 → 복구 | 확정되지 않은 상태는 동기화 대기로 표시. 재연결 후 1건만 확정 | 미실행 |
| 6 | 단절 중 새 QR 읽기 | 확인 불가 안내. 새 티켓을 자동으로 입장시키지 않음. 책임자 예외 원장 절차 사용 | 미실행 |
| 7 | 다른 기기가 먼저 처리한 대기를 나중에 동기화 | 충돌로 표시하고 서버 성공을 중복 생성하지 않음 | 미실행 |
| 8 | 취소 티켓 / 다른 회차 / 변형한 QR 확인 | 사유를 구분하여 입장 거절 | 미실행 |
| 9 | 특전 A 사용 처리 → 같은 품목 재시도·다른 기기 재시도 | 전산 지급 1회. 성공을 확인한 다음 실물 1개 전달 | 미실행 |
| 10 | 연결 단절 중 특전 지급 시도 | 확인 전 실물 지급 보류. 재연결 후 원장 확인 | 미실행 |
| 11 | 마감 집계 | 좌석별 입장·예외·특전 전산 기록과 실물 잔량 일치 | 미실행 |

상세 동작과 통신 장애 예외는 [좌석별 현장 운영](seat-level-field-operations.md)을 따른다. 기기 1대와 PC 탭 조합은 준비 점검에는 쓸 수 있으나 실제 휴대폰 2대 리허설 합격으로 기록하지 않는다.

## 소액 live 결제·환불 준비안

아직 실행하지 않았다. 검토 가능한 기본안은 **시험용 미래 회차의 1석, 티켓 1,000원 + 현재 좌석별 예매 수수료 2,000원 = 총 3,000원 1건**이다. 실제 테스트 공연/회차·결제 수단·소유자와 이 금액을 확정한 뒤 진행한다. 외화 수단은 실제 결제 화면의 통화·청구액과 별도 한도를 먼저 고정한다.

1. 공연일 이전 날짜에 결제하고 같은 KST 날짜 안에 취소한다. 현 코드의 당일 취소 경로는 서비스 수수료를 포함하지만, 실제 실행 직전 취소 미리보기의 환불액을 다시 확인한다. 관람일 당일 취소는 허용되지 않는다.
2. 소유자가 카드/지갑 인증을 직접 완료한다. 주문별 PG 승인·내부 결제·확정 예매·Ticket Item·QR을 대조한다.
3. 구매자 취소 화면의 예상 환불액을 확인하고 전체 취소한다. PG `CANCELED`/잔액 0·내부 취소·QR 회수·보류 종료 후 좌석 재개방을 확인한다.
4. 카드사/지갑의 실제 취소 반영과 가맹점 정산 원본·은행 입금을 별도로 대조한다. PG 승인 취소만으로 은행 단계까지 완료 처리하지 않는다. 카드/계좌 번호 원문은 보고서에 넣지 않는다.
5. 입장 처리한 현장용 티켓과 live 환불용 티켓을 구분한다. 이 계획으로 실제 거래나 기존 고객 환불을 자동 실행하지 않는다.

| 증거 | 현재 상태 |
| --- | --- |
| 지정 시험 주문의 실제 승인·취소 | 미실행 |
| 카드/지갑 실제 환불 반영 | 미확인 |
| PG 정산 원본과 은행 자료 대조 | 미확인 |

## 공연별 오픈 직전

1. 공개 상태, 판매 KST, 회차, 층·좌석 수, 가격·수수료, 1인 제한, 결제 수단, 한국어·영문 안내와 번역 상태를 운영 화면에서 검토한다.
2. 지정 판매·입장 시간을 Valkey maintenance 보호 구간에 넣어 [판매 posture 검사](../../scripts/managed-demo/verify-valkey-sale-posture.mjs)를 다시 실행한다. 현재 maintenance는 수요일 18:00 UTC(목요일 03:00 KST)이므로 실제 일정과 대조해야 한다.
3. 판매 최소 15분 전에 API 8대와 Web 12대를 예열한다. [현재 용량 절차](managed-demo-cost-floor.md#current-600-seat-opening-profile--2026-11-02)에 따라 실제 최소·Ready 상태·관측 인스턴스 수를 확인하고 `node scripts/managed-demo/warm-web-routes.mjs`로 홈·예매 상태 조회가 Web 12대 각각에서 성공한 것을 확인한다. API 예열 Scheduler의 정기 예약은 공연 일정이 확정되기 전 일시정지 상태를 유지한다. 0대 cold start는 정합성을 지켰지만 진입 p95 13.8초로 지연 목표에 미달했다. 예열 완료 전 판매를 시작하지 않는다.
4. 진행 중 결제·환불, 백업, worker 최근 성공, [운영 감시](launch-monitoring.md)의 활성·실제 수신·담당자 인수, 복구 대상 revision/worker 이미지를 확인한다. 판매 중 겹친 배포의 DB 연결 예산은 별도다.
5. 해당 공연의 Gate Ledger에 날짜·실행자·증거·남은 예외를 연결한다. 공연이 지정되지 않은 과거 ledger나 이 문서만으로 공개 오픈을 승인하지 않는다. #214/#223은 실제 미완료 조건이 사라질 때 닫는다.
