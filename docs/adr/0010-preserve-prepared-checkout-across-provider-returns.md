# Preserve prepared checkout across provider returns

A Prepared Checkout belongs to one Reservation and one Buyer Account. Its order ID, canonical seats, payment deadline, Checkout Payment Method and Provider Charge Quote survive full document navigation. The return page recovers this state from the authenticated API, including when no Payment exists yet. A fail URL is not evidence that a payment failed or can be cancelled.

We rejected generating another order after every SDK error: an ambiguous response or document remount can leave multiple unpaid orders and may obscure a late approval. We also rejected restoring only the order ID: the foreign payment tab then falls back to a domestic method, and a retry can cross provider accounts or currencies.

**Consequences**

- Reservation preparation stores `checkout_payment_method`. A Buyer can review a different method before Provider Handoff; the same order is updated with a new quote when needed.
- Provider Handoff means the server has validated the method and seat locks and has authorized opening that provider's checkout. `checkout_started_at` records this boundary, not proof of provider approval or of a browser actually opening.
- A conditional database update freezes the method after successful seat-lock validation and grants Provider Handoff only once, including across concurrent tabs. Concurrent method changes and handoff cannot both succeed with different method snapshots. Foreign minor-unit amounts remain server-owned.
- Before Provider Handoff, same-method retries reuse the order and quote. Such a retry needs no new prepare (and so no queue access window), but Provider Handoff is admitted by the same order binding as payment confirm (the browser session that prepared the order, or a live queue admission): a resume from another browser session is refused before the provider checkout opens, instead of leaving a handoff that only the bound session could confirm (2026-10 audit). After handoff, the browser checks the result and does not open another provider request while that result is unknown. Handoff to another method requires resolving or ending the previous checkout; an untrusted return query cannot reset the method binding.
- A pending checkout cannot be abandoned or expired by a local timeout, including when no Payment callback exists. A merchant-confirmed checkout can be explicitly ended only with the no-approval evidence below; unknown asynchronous-wallet results remain protected. Provider `IN_PROGRESS`, `DONE`, and `PARTIAL_CANCELED` block pre-payment abandonment even after the local deadline. Confirmed orders direct the Buyer to their tickets.
- Changes use an additive, nullable migration. Existing members, original payment amounts, Ticket Items, QR Credentials and audit history remain unchanged. A legacy pending order with no method snapshot cannot enter a new provider checkout. Drain/resolve these orders before cutover; do not guess a provider or currency from the UI language.
- The browser saves the order ID in its address before sending the prepare request, so a committed order survives response loss. Protected checkout login also retains this address and locale.
- Browser recovery before handoff keeps the locale, presents the original method/quote, and restores the domestic or foreign widget. The installed SDK exposes no API to select an individual wallet; the Buyer explicitly selects the saved wallet inside that widget before retrying.
- The UI distinguishes checking, ready, confirmed, ended and lookup failure. Unknown state does not become a fresh payment or automatic cancellation. A server quote is visible before requesting foreign payment.

**Validation**

Use real PostgreSQL for pending-order recovery, owner isolation, stored quote/method, pre-handoff changes, concurrent handoff, immutable post-handoff method and failed seat-lock validation. Test unknown handoffs after deadline expiry against the abandonment API, prepare API and expiration worker. Use full-page remount tests with an empty booking store, an HTTP webhook acknowledgement test and actual browser/sandbox readback. A local test does not certify production cutover or the remaining external/device gates.

**Provider lookup limits**

The [widget-key API scope](https://docs.tosspayments.com/reference/using-api/api-keys) documents payment-key lookup and transaction lookup, but does not list order-ID lookup. `NOT_FOUND_MERCHANT` is not evidence of a missing payment. The [transaction API](https://docs.tosspayments.com/reference#거래-조회) can supply a payment key when a matching transaction exists; an empty/error result is not proof that an asynchronous payment is unpaid. Unresolved handoffs stay in status review with My tickets and support actions.

Manual asynchronous-wallet checks use a stored payment key when available. When browser Back lost the return key, they query the foreign-payment MID's transaction ledger from ten minutes before order creation, then pass the unique matching key through the same verified async-return reconciliation. A successful empty ledger is a completed check with the order still pending, not a provider outage or permission to cancel. A full 5,000-row page, conflicting keys, a malformed match or a provider error remains unavailable; interactive requests do not scan unbounded history. The existing 65-second provider timeout covers the documented transaction-query latency. No payment approval or cancellation is requested by this discovery path.

**Handoffs the provider never opened (2026-10-02)**

The provider SDK can reject `requestPayment` before its checkout opens (card issuer not selected, a selection race, invalid parameters). No provider payment exists then, so no webhook ever resolves the order, and the rules above would block retry, abandonment and expiry forever. The browser treats every SDK rejection the same way, including a checkout the buyer opened and then closed (`USER_CANCEL`), which leaves a READY payment at Toss until it expires.

- The browser runs every check it can before Provider Handoff: the live widget selection, the last reported payment-terms status, the prepared method and country.
- If the SDK rejects after handoff (any rejection, including a closed checkout), or the branch response is lost or returns a 5xx, the browser asks `POST /api/v1/payments/branch/release`. The server clears `checkout_started_at` only for its owner, only for merchant-confirmed methods (card, transfer, domestic easy pay, overseas card, PayPal: Toss charges these only after this server's confirm), only within 45 seconds of the handoff, only when no Payment row exists, only while holding the order's confirm lease (no confirm in flight), and only when no confirm was ever attempted for the order. The lease alone is not enough: confirm releases it as soon as the request ends, including after a provider timeout or a failed recording that left no Payment row. Confirm therefore records an attempt marker in Valkey, while it holds the lease and before it can call Toss, that outlives the release window by far (30 minutes). Asynchronous wallets (Alipay+, TrueMoney) are never released. Any refusal leaves the order in status review, as before.
- Reusing a released order is safe only because its payment deadline is capped at 15 minutes after creation (`PAYMENT_PROCESSING_TOTAL_CAP_MS`, kept next to the release window in `payment-handoff-policy.ts`), below Toss' 30-minute READY expiry: the late EXPIRED webhook of a closed checkout can then only meet a confirmed, failed or expired order, never a retry still in progress. A test asserts the relation; raising the cap to 30 minutes or more needs another guard first.
- A re-prepare after a release may change the Checkout Payment Method. A tab of the earlier handoff that still completes and confirms is compensated, not issued: payment confirm compares the approved method with the current frozen method and the performance policy (2026-10 audit #70).
- A handoff whose release never arrived is reviewed by the pending-payment worker only after its payment deadline plus 45 minutes, when Toss has already expired and reported any checkout it opened. The worker fails it only for a merchant-confirmed method with no Payment row, a confirm lease held from before the provider lookup until the update, and successful Toss transaction lookups on every configured MID key (the MID a checkout used depends on its widget variant and confirm scope) that show no transaction for the order since before it was created. A matching transaction, a lookup error or a page-cap overflow keeps the order in review: the next review is deferred (24 hours with a daily critical log for a found transaction, 30 minutes otherwise) and the scan continues from a cursor, so unresolvable orders never block newer ones. This is provider-ledger evidence, not a local timeout; order-ID lookup is still not used. `PAYMENT_HANDOFF_ABANDON_SWEEP_ENABLED=false` turns the review off.

**Explicit checkout restart after a browser return (2026-11-10)**

The 45-second SDK release window cannot handle a Buyer who spends several minutes in a card, transfer or PayPal checkout and then returns through browser history. The UI now offers an explicit method change for these merchant-confirmed methods. Alipay+ and TrueMoney continue to wait for provider evidence because they can approve without Grabit's confirm call.

- `POST /api/v1/payments/checkout/end` is authenticated and owner-scoped. Within 15 minutes of order creation, it closes a merchant-confirmed handoff only while holding the refreshed confirm lease, with no confirm-attempt marker and no Payment row. The 30-minute marker outlives this window. Approval already started, an unavailable lease/store or an unknown method refuses the action.
- Ending writes a terminal `CANCELLED` state and preserves the original method, handoff timestamp and purchase allocations. A late callback for that order is rejected before calling Toss confirm. A retry receives a new order ID, so callbacks and expiry events from the old provider checkout cannot affect the replacement.
- `keepSelection` requires valid seat ownership, a future payment deadline and active queue admission. Under the same database transaction, add-on product locks protect copying the bound quantities into unbound holds; the ended order retains its original receipt. If these conditions do not hold, the Buyer returns to seat selection after unlock completes.
- Repeated end requests are idempotent. Reselection from an ended-order address uses its saved showtime even after browser state is lost. Terminal reservations are displayed as ended despite their retained handoff timestamp.
- One Buyer can have only one pending checkout per showtime. New-order insertion is serialized under a transaction-scoped advisory lock for the Buyer and showtime (the existing account key-share lock only protects withdrawal); seat recovery and conflicting prepares route to the existing order before its protected seats can be mixed into a new selection.
- Old merchant-confirmed orders use the same all-MID transaction review and grace period as the worker. Manual status review is scoped to the Buyer and order and does not advance the worker cursor. Empty or failed Alipay lookup remains inconclusive and never permits local cancellation.

Regression coverage includes real PostgreSQL/Valkey close-versus-confirm exclusion, delayed callback refusal, add-on quantity/receipt preservation, owner isolation, concurrent replacement preparation, all four merchant-confirmed UI variants and terminal-order reselection. Production smoke must additionally enter each enabled provider checkout, return without payment approval, and verify the server state and seat release.
