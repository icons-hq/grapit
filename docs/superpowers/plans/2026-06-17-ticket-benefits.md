# Ticket Benefits Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add showtime-level ticket benefit configuration, limited-benefit random assignment, included-benefit entitlements, QR-based benefit redemption, admin records/exports, rollback, and buyer/staff visibility.

**Architecture:** `Ticket Item` remains the atomic entitlement. `Included Ticket Benefits` come from the active `Benefit Configuration` and apply to every eligible active `Ticket Item`; `Limited Ticket Benefits` are generated by live/test `Benefit Runs` and live runs replace the active limited assignments for one showtime. Benefit redemption is online and QR-based, separate from venue entry, and locks further benefit configuration/result changes for that showtime.

**Tech Stack:** Next.js 16, React 19, NestJS 11, Drizzle ORM, PostgreSQL, Zod shared contracts, TanStack Query, Vitest, Playwright, pnpm.

## Resolved Domain Rules

- A `Benefit Configuration` belongs to one showtime and is active immediately after save.
- `Included Ticket Benefits` apply immediately to all eligible active `Ticket Items` until `Benefit Result Lock`, including tickets sold after a live run.
- `Limited Ticket Benefits` require a `Benefit Run`; live runs replace current active limited assignments for that showtime.
- A `Ticket Item` can have every eligible included benefit and at most one limited benefit.
- Limited benefit quantity counts Ticket Item-level assignments, not distinct buyers.
- Eligibility is active Ticket Items in configured ticket tiers, not admission state, floor, section, buyer segment, or payment method.
- Benefit selection priority decides limited-benefit assignment order.
- Mutually exclusive limited benefits exclude the same buyer across that buyer's Ticket Items in the active showtime result.
- `6:1` and `PRE-SIGNED POLAROID` are mutually exclusive.
- Test runs can use active or unsaved configuration snapshots, create records/CSV, and never attach assignments.
- Test runs cannot be promoted to active configuration and cannot be rollback sources.
- Live runs use a system-generated seed; test runs may use an operator-provided seed.
- Live run and rollback require confirmation because they replace Buyer-visible limited assignments.
- Rollback can restore only previous live run records and skips Ticket Items that are no longer active.
- Any benefit redemption creates `Benefit Result Lock`; after that, configuration changes, live runs, and rollback are blocked for that showtime.
- Benefit redemption is online, QR-based, one benefit entitlement at a time, and uses the same scanner authority as field check-in.
- Benefit redemption records keep redacted QR references only; raw QR tokens are never stored in records or exports.
- Duplicate benefit use is `Duplicate Benefit Redemption`, separate from `Duplicate Scan`.
- Buyer ticket detail shows benefit entitlements and redemption state; no outbound notification is sent.
- CSV entitlement exports are one row per benefit entitlement/result.
